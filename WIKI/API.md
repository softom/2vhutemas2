# API проекта

Единственная точка записи данных нового контура. Веб-интерфейс, будущий Telegram-бот и навык наполнения проходят через одни и те же проверки прав и правила версий ([Р-02](Решения.md)).

- **Адрес:** `https://2vhutemas.ru/api/v1`
- **Формат:** JSON в UTF-8; файлы — `multipart/form-data`.
- **Состояние:** маршруты ниже работают и проверяются прогоном `tools/smoke.sh`. Старый контур (`/api/timeline`, `/api/media`) живёт отдельно и этим контрактом не описывается.

## Принципы, без которых записать не получится

Это не пожелания к оформлению: сервер проверяет их и отказывает.

### Связь требует обоснования

Связь двух сущностей не существует без объяснения, на каком основании она проведена. `POST /links` без непустого обоснования возвращает `422 link_requires_justification`. Обоснование создаётся той же операцией в одной транзакции — связь без него не сохранится даже при сбое на полпути.

Связать можно что угодно с чем угодно: фильм со зданием, постановку с театром. Свобода связи оплачивается обязанностью объяснить, почему она есть.

Упоминание объекта в тексте связью **не является** и обоснования не требует: это ссылка документа, она живёт в блоках и попадает в указатель вхождений.

### Тип — узел дерева, а не отдельный вид записи

Запись одна для всех: человек, здание и стиль отличаются типом, а не строением ([Р-37](Решения.md)). Тип обязателен и берётся из дерева `entity_types` в `capabilities`: корневые ветви `who`, `what`, `when` — это прежние виды записи, ниже растут типы вроде `architecture_object` или `performance`.

- Отбор идёт по ветви целиком: `?type=what` вернёт и здания, и постановки, `?type=architecture_object` — только здания.
- Прежнее `kind` (`person`, `object`, `period`) принимается как псевдоним корневой ветви — и в теле запроса, и в фильтре. Выданные раньше сценарии наполнения работают без правки.
- Тип можно сменить правкой: значения и прикреплённое от этого не теряются.
- В ответах карточки и каталога приходят `type`, `type_title` и `type_path` — путь от корневой ветви вниз.

### Величины — параметры, а не колонки

Предметные величины хранятся параметрами ([Р-38](Решения.md)). Параметр — определение величины: код, название, единица и то, что именно считается этой величиной. Набор — список параметров, привязанный к узлу дерева типов; он действует и для всего, что ниже. Показатели — одно измерение целиком у записи: «по проекту», «после реконструкции».

- Что подсказано записи её ветвью, отдаёт `GET /parameters/for-type/{код типа}`.
- Дата и место — такие же величины: `value_type: "date"` и `value_type: "place"`. Ответ «место» — ссылка на запись типа «Место» (`place_id` — её номер); заводятся и находятся места через `/places` ([Р-85](Решения.md)).
- Собственный текст записи — тоже значение параметра, «Текст» (`value_type: "blocks"`), но правится он полем `body_json` карточки, а не списком величин ([Р-86](Решения.md)).
- У некоторых вопросов бывает несколько ответов: две реконструкции, два адреса. Такие параметры помечены `is_repeatable`. У величин для сравнения ответ один.
- Заполненное приходит в карточке полем `indicators`, задаётся целиком через `PUT /entities-indicators/{id}`.
- Отбор и сортировка считают по показателям с `is_current`; в карточке видны все.
- Единица измерения живёт в определении параметра, рядом со значением её нет.
- Справочник ведёт обладатель `su`: «вместимость зала» и «Вместимость (мест)», заведённые порознь, делают сравнение бессмысленным.

### Даты и места — такие же величины

Дата и место не отдельные сущности, а ответы на вопросы «когда» и «где» ([Р-39](Решения.md)). Вид даты (проектирование, открытие) и роль места (адрес объекта, место рождения) — это параметры со значением-датой и значением-местом.

У объекта не одна дата: замысел, начало строительства, открытие, реконструкция, утрата приходятся на разные годы. Датировки по-прежнему можно задать списком через `PUT /entities-dates/{id}` — маршрут сохранён и переводит список в значения параметров. Виды дат берутся из `GET /parameters` (это параметры с `value_type: "date"`), словаря `date_kinds` больше нет.

- **Неизвестное остаётся пустым.** Нет сведений о месяце — месяц не указывается; нет даты вовсе — она не выдумывается.
- **Приблизительность отмечается признаком** `is_approximate`, а не сдвигом года. «Около 1930» — это `start_year: 1930, is_approximate: true`.
- **Незавершённое** отмечается `is_ongoing: true` и остаётся без конечного года.
- Год может быть отрицательным — это даты до нашей эры.
- Конец раньше начала отклоняется.

### Остальное, о чём стоит знать заранее

- **Место** — запись типа «Место», такая же, как человек или здание: свои сведения, своя страница. Ставится ответом величины записи: адрес объекта, место рождения, захоронение, офис организации; причина — в пояснении к значению (`note`). Одно место переиспользуется многими записями ([Р-85](Решения.md)).
- **Изображение** — запись типа «Изображение»; прикрепление к записи — связь «Иллюстрация» ([Р-84](Решения.md)).
- **Метка** — слово из общего справочника. Регистр и лишние пробелы двойников не создают, решётка в базу не попадает ([Р-29](Решения.md)).
- **Изображение** хранится в медиатеке, а в тексте живёт ссылкой по идентификатору. Оригинал неизменен; экранную версию и превью делает сервер.
- **Каждое изменение создаёт версию.** Правка присылает версию, от которой началась; если материал успели изменить, придёт `409 version_conflict`, и чужая работа не затрётся.
- **Черновик не виден постороннему.** Пока материал не опубликован, карточка, текст и файлы отдаются только тем, у кого есть права.

## Вход и права

Токен выдаёт Supabase Auth, API проверяет подпись:

```
Authorization: Bearer <access_token>
```

Без токена доступно чтение опубликованного. Участник заводится при первом входе и прав не получает: роли назначает администратор.

| Право | Что открывает |
|---|---|
| `view` | Просмотр доступных материалов |
| `edit` | Правка существующих, привязка мест, файлов и меток |
| `create_delete` | Создание объектов, связей, файлов, мест |
| `publish` | Публикация своей версии |
| `review` | Рассмотрение чужих версий |
| `su` | Полный административный доступ |

`GET /me` возвращает участника и его действующие права.

## Ошибки

```json
{ "error": { "code": "version_conflict", "message": "…", "details": {}, "request_id": "…" } }
```

Код латиницей — для программы, сообщение по-русски — для человека. `owned_content` означает попытку править или публиковать отдельно то, что принадлежит записи целиком — её собственный текст ([Р-78](Решения.md)); в `details` приходит владелец. Коды: `validation_failed` (400), `unauthenticated` (401), `permission_denied` (403), `not_found` (404), `version_conflict`, `duplicate` и `owned_content` (409), `payload_too_large` (413), `link_requires_justification` (422), `internal_error` (500).

## Маршруты

### Справочники и служебное

| Маршрут | Что делает |
|---|---|
| `GET /health` | Живость сервиса и задержка базы |
| `GET /capabilities` | Версия контракта, лимиты, дерево типов записей (`entity_types`), словари (`link_roles`, `media_kinds` — виды изображения) и отображения по типу (`presentations`: для каждого типа компоненты режимов `compact`, `card` и `editor`; редактор собирает форму из разделов `title`, `tags`, `indicators`, `gallery`, `text`) |
| `GET /me` | Участник и его права |
| `POST /session` | Меняет токен на короткоживущую куку для показа приватных файлов в теге изображения |

Коды словарей берутся из `capabilities`, а не придумываются.

### Объекты, участники, периоды

| Маршрут | Что делает |
|---|---|
| `GET /entities?type=&q=&cursor=&limit=&archived=1` | Каталог с отбором по ветви дерева типов и поиском по названию. Архив не показывается; `archived=1` возвращает и его — для поиска убранного. У каждой записи — `compact`: её компактный вид с готовыми значениями (`thumbnail`/`portrait` с номером файла обложки в `asset`, `mark`, `parameter` со значением в `value`); тот же `compact` приходит в `GET /entities/{id}` |
| `GET /entities?parameter=&min=&max=&sort=parameter&order=desc` | Сортировка по величине; `min` и `max` отбирают по диапазону. Запись без величины не прячется, а уходит в конец. В ответе приходит `parameter_value`; при сортировке по величине постраничный указатель не выдаётся |
| `GET /entities?values=код,код` | Список отдаёт значения названных величин в поле `values` — чтобы показать их колонками |
| `GET /entities/{id}` | Карточка: свойства, тип и путь по дереву, показатели (включая даты и места), файлы, метки, ссылка на описание, текущая версия. Вместо номера можно прислать слаг — текущий или прежний. Также приходят `sources` (источники; гостю — опубликованные), `authors` (подписи материала), `canonical_url` и `citation` — готовые ссылки ГОСТ и APA ([Р-65](Решения.md)) |
| `POST /entities` | Создание; требует `create_delete` |
| `PATCH /entities/{id}` | Правка; требует `edit` и `base_revision_id`. Одним запросом принимает свойства, `body_json` (собственный текст), `indicators` и `tags` — всё сохраняется одной версией |
| `POST /entities/{id}/publish` | Публикация записи целиком вместе с текстом; требует `publish` |
| `GET /entities/{id}/versions` | История редакций: какая публичная, какая в работе, кто правил |

```json
POST /entities
{
  "type": "architecture_object",
  "slug": "novosibirskiy-teatr-opery-i-baleta",
  "title_ru": "Новосибирский театр оперы и балета",
  "title_en": "Novosibirsk Opera and Ballet Theatre",
  "profile": { "typology": "Театр" }
}
```

Ответ: `{ "id": 17, "material_id": "…", "revision_id": "…" }`. Возвращённый `revision_id` присылается в следующей правке как `base_revision_id`.

`slug` — только строчные латинские буквы, цифры и дефис, уникален среди всех записей. Прежний адрес сохраняется, старые ссылки не ломаются.

`profile.typology` — временное поле: на следующем этапе типология станет значением параметра ([Р-38](Решения.md)).

**Запись хранит свой текст сама** ([Р-78](Решения.md)). Описание — не отдельный объект со своей публикацией, а содержимое записи: приходит в карточке как `body_json` и правится вместе с ней.

```json
PATCH /entities/17
{
  "base_revision_id": "…",
  "title_ru": "Новосибирский театр оперы и балета",
  "body_json": [
    { "id": "b1", "type": "paragraph",
      "content": [{ "type": "text", "text": "Зал под сводом купола.", "styles": {} }] }
  ],
  "indicators": [ … ],
  "tags": ["купол"]
}
```

Что не прислали — то не меняется: правка одного названия текст не стирает. Ответ содержит новый `revision_id`; он же нужен как `base_revision_id` в следующей правке.

### Параметры и показатели

| Маршрут | Что делает |
|---|---|
| `GET /parameters` | Справочник: код, название, единица, тип значения, определение, сколько раз заполнен |
| `GET /parameters/for-type/{код}` | Что подсказано этому типу: наборы его ветви сверху вниз |
| `POST /parameters`, `PATCH /parameters/{id}`, `DELETE /parameters/{id}` | Ведение справочника; требует `su`. Тип значения у заполненного параметра не меняется, заполненный параметр не удаляется |
| `GET /parameter-sets` | Наборы с составом и ветвями, к которым привязаны |
| `POST /parameter-sets`, `PATCH /parameter-sets/{код}`, `DELETE /parameter-sets/{код}` | Завести набор, переименовать, убрать; требует `su` |
| `PUT /parameter-sets/{код}/items` | Состав набора целиком: список параметров с подсказками; требует `su` |
| `POST /parameter-sets/{код}/types`, `DELETE /parameter-sets/{код}/types/{тип}` | Привязать набор к узлу дерева и отвязать; требует `su` |
| `POST /parameter-sets/{код}/entities`, `DELETE /parameter-sets/{код}/entities/{id}` | Прикрепить набор к отдельной записи и снять; требует `edit` |
| `GET /entities/{id}/parameters` | Что подсказано этой записи: величины её ветви плюс прикреплённые лично ей |
| `PUT /entities-indicators/{id}` | Показатели записи целиком; требует `edit` и создаёт версию записи |

Типы значений: `number`, `integer`, `text`, `boolean`, `option` (список), `date`, `place` (ссылка на запись «Место»; в базе это ответ-запись `entity` с ветвью «Где»), `blocks` (текст записи — только параметр «Текст», правится полем `body_json`).

**Список** задаётся значениями параметра (`options`) и отвечается кодом значения, а не текстом. Одиночный и множественный списки — один тип: множественный помечается `is_repeatable`, и тогда у параметра допустимо несколько ответов в одних показателях. В ответах приходят и код (`option`), и название (`option_title`).

```json
PUT /entities-indicators/17
{
  "base_revision_id": "…",
  "indicators": [
    {
      "title": "По проекту",
      "is_current": true,
      "measured_year": 1931,
      "values": [
        { "parameter": "hall_capacity", "num_value": 3000 },
        { "parameter": "typology", "text_value": "Театр" },
        { "parameter": "opening", "date_start_year": 1945 },
        { "parameter": "address", "place_id": "…" }
      ]
    }
  ]
}
```

Незаполненное не пишется: величина без ответа просто отсутствует. Значение не того типа отклоняется — параметру с типом «текст» число не подойдёт.

**Набор у отдельной записи** — исключение из наследования по дереву: большепролётное покрытие есть и у вокзала, и у рынка, а не у типа целиком. Прикрепляется правом `edit`:

```json
POST /parameter-sets/large_span_roof/entities
{ "entity_id": 17 }
```

После этого величины набора приходят в `GET /entities/17/parameters` и заполняются как обычно. Привязка набора к ветви дерева меняет подсказку для всех записей под ней и потому требует `su`.

Прежнее `profile.typology` при создании и правке записи по-прежнему принимается и ложится значением параметра `typology`.

### Датировки

```json
PUT /entities-dates/17
{ "dates": [
  { "kind": "design", "start_year": 1929 },
  { "kind": "construction_start", "start_year": 1931 },
  { "kind": "opening", "start_year": 1945, "start_month": 5, "start_day": 12 },
  { "kind": "reconstruction", "start_year": 2003, "end_year": 2005, "is_approximate": true }
] }
```

Список задаётся целиком: присланное заменяет прежнее.

### Тексты

Собственный текст записи (описание, лекция) — значение её параметра «Текст»: правится через `PATCH /entities/{id}` полем `body_json` и публикуется вместе с записью ([Р-78](Решения.md), [Р-86](Решения.md)). **Самостоятельный текст — запись типа «Документ»** со своим текстом ([Р-84](Решения.md)):

```json
POST /entities
{ "type": "document", "slug": "o-kupolnyh-pokrytiyah",
  "title_ru": "Материал о теории купольных покрытий",
  "body_json": [
    { "id": "b1", "type": "heading",
      "content": [{ "type": "text", "text": "Купол и сцена", "styles": {} }] },
    { "id": "b2", "type": "paragraph",
      "content": [{ "type": "text", "text": "Зал под сводом купола.", "styles": {} }] },
    { "id": "b3", "type": "mediaImage",
      "props": { "assetId": "…", "caption": "Общий вид", "variant": "screen" } }
  ] }
```

| Маршрут | Что делает |
|---|---|
| `POST /documents` | Больше не заводит текст: `409 owned_content` с подсказкой — самостоятельный текст заводится как запись «Документ» |
| `GET /documents/{id}` | Прежний текст — история; читается как текст своего хозяина |
| `PATCH /documents/{id}` | `409 owned_content`: у каждого прежнего текста есть хозяин — запись или связь, правится он там |

Тело текста — блоки BlockNote. Собственные блоки проекта:

- `entityCard` — карточка записи отдельным блоком, `props: { entityId, occurrenceId }`;
- `entityMention` — упоминание внутри абзаца, те же свойства, но внутри `content`. Как оно выглядит — решает компактный вид типа: здание с миниатюрой, человек с портретом, источник со знаком ([Р-86](Решения.md));
- `sourceRef` — знак источника внутри абзаца, `props: { entityId, linkId, occurrenceId, title, note }` ([Р-80](Решения.md));
- `mediaImage` — изображение из медиатеки, `props: { assetId, caption, variant }`; `assetId` — номер файла;
- `modelEmbed` — интерактивная модель сайта в выделенной рамке, `props: { src, title, caption, height }`; `src` только вида `/models/имя.html`, прочие адреса не показываются ([Р-83](Решения.md)).

Сервер сам извлекает текст для поиска и указатель вхождений объектов. Ссылка на несуществующий объект отклоняется. Неизвестные типы блоков сохраняются без потери.

### Медиатека

Изображение — запись типа «Изображение» ([Р-84](Решения.md)): подпись — её название, остальные сведения — параметры набора «Изображение — сведения», публикация — публикация записи. Номер файла (`id`, UUID) остаётся адресом файла и значением `assetId` в тексте; номер записи приходит полем `entity_id`.

| Маршрут | Что делает |
|---|---|
| `GET /media?q=&cursor=&needs=attribution` | Список файлов: варианты, метки, сведения; `needs=attribution` — только ждущие автора и источника |
| `POST /media` | Загрузка оригинала, `multipart/form-data`; вместе с файлом заводится его запись-черновик |
| `GET /media/{id}` | Сведения о файле |
| `PATCH /media/{id}` | Правка сведений; файл не меняется. `visibility: "public"` публикует запись, `"private"` снимает с публикации |
| `GET /media/{id}/file?variant=thumbnail\|screen\|original` | Выдача файла; без входа — только у опубликованной записи |
| `POST /media/attachments` | Прикрепление к записи — связь «Иллюстрация»; встаёт в конец, `role: "cover"` отмечает её главной (`is_primary`); обложка — первое изображение по порядку ([Р-36](Решения.md)) |
| `PUT /media/attachments/order` | Порядок изображений у записи: список связей целиком |
| `DELETE /media/attachments/{id}` | Открепление: связь уходит в архив |
| `POST /media/{id}/derivatives` | Повтор обработки после ошибки |

Номер привязки (`attachment_id`) — номер связи. В окружении записи (`GET /links`) иллюстрации не показываются: у них своё место — галерея карточки.

Поля формы загрузки и правки: `file`, `caption` (название записи), `kind` (вид изображения, коды — `media_kinds` в `capabilities`), `author` (фотограф или чертёжник), `credit` (правообладатель), `source_url`, `original_caption` (подпись в источнике), `holder` (место хранения), `inventory_no`, `created_year`, `license`, `alt` (описание для незрячих), `description`, `keywords` (через запятую — станут метками записи). Пустое поле в правке — «не менять». Контрольную сумму, размеры, экранную версию и превью сервер делает сам.

Файл передаёт клиент; сервер не скачивает произвольные адреса.

### Места

Место — запись типа «Место» ([Р-85](Решения.md)): страна, населённый пункт, улица, дом, помещение, широта, долгота, точность, источник сведений — параметры набора «Место — сведения». У места своя страница и версии. Маршруты ниже — удобный вход редактора адреса; номер места — номер записи.

| Маршрут | Что делает |
|---|---|
| `GET /places?q=` | Поиск мест; требует `edit` |
| `POST /places` | Новое место — новая опубликованная запись |
| `PATCH /places/{id}` | Правка сведений места; пустое поле — «не менять» |
| `GET /places/{id}/usage` | В каких записях место стоит ответом |

Отношение к месту — величина той записи, что на него ссылается: «адрес объекта», «место рождения», «захоронение», «офис организации». Причина — пояснение к значению (`note`).

```json
POST /places
{ "country": "Россия", "settlement": "Новосибирск",
  "street": "Красный проспект", "house": "36",
  "lat": 55.030476, "lon": 82.924856, "precision": "building" }
```

Ответ: `{ "id": "1015", "reused": false }`. Дальше номер ставится значением:

```json
PUT /entities-indicators/17
{ "base_revision_id": "…",
  "indicators": [ { "title": "Сведения",
    "values": [ { "parameter": "address", "place_id": "1015",
                  "note": "стоит здесь с 1945 года" } ] } ] }
```

Координаты указываются парой. Пустое место не создаётся. Точность: `point`, `building`, `settlement`, `region`.

**Повтор адреса не заводит второе место.** Совпадение ищется без учёта регистра и лишних пробелов: «Красный проспект» и «красный  проспект » — одно место. Если такое уже есть, возвращается его номер с пометкой `reused: true` и кодом 200 вместо 201; недостающие координаты при этом дописываются.

### Связи

| Маршрут | Что делает |
|---|---|
| `POST /links` | Создание связи вместе с обоснованием |
| `GET /links?entity_id=` | Окружение объекта с обоснованиями. Гостю — только связи с опубликованными записями |
| `GET /links/mentions?entity_id=` | В каких опубликованных материалах объект упомянут |
| `POST /links/{id}/publish` | Публикация связи вместе с её обоснованием; требует `publish` |
| `DELETE /links/{id}` | Архивирование: связь уходит из показа, версии и обоснование остаются |

```json
POST /links
{ "from_entity_id": 17, "to_entity_id": 21, "role": "influence",
  "justification": { "text": "Оба случая показывают зрителя внутри зрелища." } }
```

Вместо `text` можно прислать `body` — блоки BlockNote.

Обоснование — содержимое самой связи, у него нет отдельной публикации: связь публикуется вместе с ним ([Р-78](Решения.md)).

### Метки

| Маршрут | Что делает |
|---|---|
| `GET /tags?q=` | Справочник с числом использований |
| `PUT /tags/entities/{id}` | Метки объекта, списком целиком |
| `PUT /tags/media/{id}` | Метки файла |

### Публикация и рассмотрение

**Запись и связь публикуются целиком** — сведения, величины, метки и собственный текст одной редакцией ([Р-78](Решения.md)). Отдельной публикации текста нет.

| Маршрут | Что делает |
|---|---|
| `POST /entities/{id}/publish` | Публикация записи; требует `publish` |
| `POST /links/{id}/publish` | Публикация связи с обоснованием; требует `publish` |
| `GET /entities/{id}/versions` | История редакций записи: публичная, рабочая, кто и когда правил |

```json
POST /entities/17/publish
{ "note": "первая публикация" }
```

По умолчанию публикуется рабочая редакция — та, что получилась последней правкой. Можно указать `revision_id` и тем вернуть прежнюю. Повторная публикация той же редакции отклоняется. Публиковать можно только полную редакцию: частичные версии, оставшиеся от прежней модели, в истории видны, но публикации не подлежат.

**Материалы** остаются единицей авторства и истории, а для независимых объектов — файлов и самостоятельных текстов — ещё и способом публикации.

| Маршрут | Что делает |
|---|---|
| `GET /materials/{id}` | Состояние: черновик или опубликовано, какая версия опубликована, ход рассмотрения |
| `POST /materials/{id}/publish` | Публикация независимого объекта. Для записи или связи вызов сработает, но правильный адрес — у владельца |
| `POST /materials/{id}/submit` | Отправка версии на рассмотрение; требует `edit` |
| `POST /materials/{id}/review` | Решение по чужой версии: `approved` или `rejected`; требует `review` |
| `DELETE /materials/{id}` | Архивирование: уходит из показа, история и файлы остаются |

**Кто без права `publish`** отправляет версию через `submit`: материал при этом не меняется, читатель продолжает видеть прежнее. Обладатель `review` принимает или отклоняет; принятие означает публикацию.

Публикация объекта делает публично видимыми его карточку, датировки, места и метки. Прикреплённые файлы становятся доступны, когда опубликован их собственный материал.

## Порядок наполнения одного объекта

1. `GET /capabilities` — взять дерево типов и коды словарей.
2. `POST /entities` — создать запись, запомнить `id` и `revision_id`.
3. `GET /parameters/for-type/{код типа}` — узнать, какие величины подсказаны этому типу.
4. `PUT /entities-indicators/{id}` — заполнить величины: числа, тексты, списки, даты и места.
5. `POST /media` — загрузить изображения (каждое станет записью «Изображение»), затем `POST /media/attachments` на каждое — связь «Иллюстрация».
6. `PATCH /entities/{id}` с `body_json` — описание; изображения внутри вставляются блоком `mediaImage`. Сюда же можно передать `indicators` и `tags`, если удобно одним запросом.
7. `PUT /tags/entities/{id}` — метки.
8. `POST /links` — связи с другими записями, каждая с обоснованием.
9. `POST /entities/{id}/publish` — публикация, если есть право `publish`.

Место заводится или переиспользуется через `POST /places` — это запись «Место», — а к записи ставится ответом величины с типом «место».

До публикации материал остаётся черновиком и посторонним не виден.

## Как создать и править лекцию

Лекция — обычная запись типа `lecture` в ветви «Служебные». Отдельных маршрутов у неё нет: текст — собственное содержимое записи, ссылки на объекты — блоками внутри текста, номер и курс — величинами. Ниже порядок целиком; он проверен на сервере правами сессии наполнения.

**1. Создать запись.**

```json
POST /entities
{
  "type": "lecture",
  "slug": "lekciya-03-zrelischnye-zdaniya",
  "title_ru": "Лекция 3. Зрелищные здания"
}
```

Ответ: `{ "id": 150, "material_id": "…", "revision_id": "…" }`. `revision_id` понадобится в следующей правке.

**2. Заполнить номер и курс.** Величины лекции: `lecture_number` (целое число) и `course` (текст). Что подсказано типу — всегда можно спросить у `GET /parameters/for-type/lecture`.

```json
PUT /entities-indicators/150
{
  "base_revision_id": "…",
  "indicators": [
    { "title": "Сведения", "is_current": true,
      "values": [
        { "parameter": "course", "text_value": "История архитектуры XX века" },
        { "parameter": "lecture_number", "num_value": 3 }
      ] }
  ]
}
```

Ответ возвращает новый `revision_id`: правка показателей создаёт версию записи, поэтому дальше нужно ссылаться на неё, а не на прежнюю.

**3. Написать текст со ссылками на объекты.** Текст лекции — её собственное содержимое: он сохраняется полем `body_json` вместе с записью. Объекты вставляются блоками: `entityCard` — карточкой отдельным блоком, `entityMention` — ссылкой внутри абзаца.

```json
PATCH /entities/150
{
  "base_revision_id": "…",
  "body_json": [
    { "id": "b1", "type": "paragraph",
      "content": [{ "type": "text", "text": "Зал без опор появился раньше, чем его смогли построить.", "styles": {} }] },
    { "id": "b2", "type": "entityCard", "props": { "entityId": "38", "occurrenceId": "o1" } },
    { "id": "b3", "type": "paragraph",
      "content": [
        { "type": "text", "text": "Сравните с ", "styles": {} },
        { "type": "entityMention", "props": { "entityId": "49", "occurrenceId": "o2" } },
        { "type": "text", "text": " — там задача решена иначе.", "styles": {} }
      ] }
  ]
}
```

`occurrenceId` — произвольный устойчивый идентификатор появления; по нему сервер собирает указатель вхождений. Ссылка на несуществующую запись отклоняется.

**Вставка в текст связью не является:** это ссылка на запись и её отображение. Если лекция утверждает отношение между записями — заводите связь отдельно через `POST /links`, с обоснованием.

**4. Править.** Название, адрес страницы, тип и текст — `PATCH /entities/{id}` с `base_revision_id`; величины — им же полем `indicators` или отдельно через `PUT /entities-indicators/{id}`, список задаётся целиком.

```json
PATCH /entities/150
{ "base_revision_id": "…", "title_ru": "Лекция 3. Зрелищные здания XX века" }
```

Версия у лекции одна на всё: правка названия, величин и текста создаёт одну редакцию. Текущую берите из `latest_revision_id` в `GET /entities/150`. Устаревшая версия даёт `409 version_conflict` с текущей в `details` — перечитайте и повторите.

**5. Опубликовать.**

```json
POST /entities/150/publish
{}
```

До публикации лекция посторонним не видна. После — попадает на страницу лекций и в упоминания тех объектов, о которых написана.

**Что стоит знать.** Курс — пока текст; когда курсы будут названы, он станет списком, и тогда в `values` поедет `option` с кодом значения вместо `text_value`. Номер не обязателен: лекция без номера не пропадёт, а встанет в конец списка.

## Страницы сайта и служебные файлы

Не часть `/api/v1`: эти адреса отвечают HTML и текстом для поисковиков и ссылок ([Р-65](Решения.md)). Caddy присылает в API всё, для чего нет файла сборки клиента.

| Адрес | Ответ |
|---|---|
| `/`, `/objects`, `/authors`, `/lectures` | Страница клиента с заголовком, описанием, JSON-LD и списком опубликованных записей |
| `/about`, `/about/{logo,philosophy,manifest}` | То же для раздела «О проекте»; неизвестный подраздел — 404 |
| `/entities/{slug}` | Готовая страница записи: сведения, связи с обоснованиями, описание, изображения, источники, «Как цитировать», JSON-LD. Номер записи или прежний слаг — 301 на текущий слаг; черновик и неизвестный адрес — 404 |
| `/login`, `/media`, `/parameters`, `/entities/new`, `/entities/{id}/edit` | Пустая оболочка клиента с `noindex` |
| `/robots.txt`, `/sitemap.xml` | Служебные файлы; sitemap — из опубликованных записей с датой правки |
| `/{INDEXNOW_KEY}.txt` | Ключ IndexNow, если он задан в настройках API |
| прочее | 404 с оболочкой клиента |

Шаблон — собранная `index.html` клиента; путь задаёт `WEB_INDEX_HTML` (по умолчанию `/web/index.html` в контейнере). Внешний адрес сайта — `SITE_URL` (по умолчанию `https://2vhutemas.ru`). Нет шаблона — 503 и запись в журнал.

После публикации записи (`POST /entities/{id}/publish`, публикация материала независимого объекта, одобрение при рассмотрении) API отправляет адрес записи в IndexNow, если задан `INDEXNOW_KEY`.

## Чего пока нет

Спроектировано, но не реализовано; выдавать за работающее нельзя:

- восстановление записи из архива (история редакций есть: `GET /entities/{id}/versions`, а вернуть прежнюю редакцию можно, опубликовав её по `revision_id`);
- пакетный импорт и проверка пакета;
- управление пользователями и ролями;
- подтверждение Telegram;
- восстановление материала из архива (само архивирование работает: `DELETE /materials/{id}`).

Ограничения и параметры — [Параметры проекта](Параметры%20проекта.md). Модель данных — [Структура БД](Схема%20данных.md). Принятые решения — [Решения](Решения.md). Исходник навыка наполнения — [SKILL.md](../skills/2vhutemas-content/SKILL.md); его текст ещё описывает API как нереализованный и требует обновления.


### Единые элементы интерфейса (Р-74, Р-75)

- `GET /api/v1/site-header?path=...`: один HTML меню и `viewer` (`authenticated`, `displayName`, `permissions`). Используется и приложением, и готовой карточкой; `private, no-store`.
- `GET /api/v1/entities/:key/card`: тот же HTML-рендер карточки, что на прямом URL; `html`, `title`, `path`. Авторизация штатная, черновики доступны по `canSeeDrafts`, гостю 404. Ответ `private, no-store`. Никаких сохранений этот маршрут не выполняет.
