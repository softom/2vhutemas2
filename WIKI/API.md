# API проекта

Единственная точка записи данных нового контура. Веб-интерфейс, будущий Telegram-бот и навык наполнения проходят через одни и те же проверки прав и правила версий ([Р-02](Решения.md)).

- **Адрес:** `https://2vhutemas.ru/api/v1`
- **Формат:** JSON в UTF-8; файлы — `multipart/form-data`.
- **Состояние:** маршруты ниже работают и проверяются прогоном `tools/smoke.sh`. Старый контур (`/api/timeline`, `/api/media`) живёт отдельно и этим контрактом не описывается.

## Принципы, без которых записать не получится

Это не пожелания к оформлению: сервер проверяет их и отказывает.

### Связь требует обоснования

Связь двух сущностей не существует без объяснения, на каком основании она проведена. `POST /links` без непустого обоснования возвращает `422 link_requires_justification`. Обоснование создаётся той же операцией в одной транзакции — связь без него не сохранится даже при сбое на полпути.

Связать можно что угодно с чем угодно: фильм со зданием, постановку с театром. Свобода связи оплачивается обязанностью объяснить, почему она есть.

Упоминание объекта в тексте связью **не является** и обоснования не требует: это ссылка документа, она живёт в блоках и попадает в указатель вхождений.

### Тип — узел дерева, а не отдельный вид записи

Запись одна для всех: человек, здание и стиль отличаются типом, а не строением ([Р-37](Решения.md)). Тип обязателен и берётся из дерева `entity_types` в `capabilities`: корневые ветви `who`, `what`, `when` — это прежние виды записи, ниже растут типы вроде `architecture_object` или `performance`.

- Отбор идёт по ветви целиком: `?type=what` вернёт и здания, и постановки, `?type=architecture_object` — только здания.
- Прежнее `kind` (`person`, `object`, `period`) принимается как псевдоним корневой ветви — и в теле запроса, и в фильтре. Выданные раньше сценарии наполнения работают без правки.
- Тип можно сменить правкой: значения и прикреплённое от этого не теряются.
- В ответах карточки и каталога приходят `type`, `type_title` и `type_path` — путь от корневой ветви вниз.

### Величины — параметры, а не колонки

Предметные величины хранятся параметрами ([Р-38](Решения.md)). Параметр — определение величины: код, название, единица и то, что именно считается этой величиной. Набор — список параметров, привязанный к узлу дерева типов; он действует и для всего, что ниже. Показатели — одно измерение целиком у записи: «по проекту», «после реконструкции».

- Что подсказано записи её ветвью, отдаёт `GET /parameters/for-type/{код типа}`.
- Дата и место — такие же величины: `value_type: "date"` и `value_type: "place"`. Место передаётся ссылкой на справочник (`place_id`), сам справочник — в `/places`.
- У некоторых вопросов бывает несколько ответов: две реконструкции, два адреса. Такие параметры помечены `is_repeatable`. У величин для сравнения ответ один.
- Заполненное приходит в карточке полем `indicators`, задаётся целиком через `PUT /entities-indicators/{id}`.
- Отбор и сортировка считают по показателям с `is_current`; в карточке видны все.
- Единица измерения живёт в определении параметра, рядом со значением её нет.
- Справочник ведёт обладатель `su`: «вместимость зала» и «Вместимость (мест)», заведённые порознь, делают сравнение бессмысленным.

### Даты и места — такие же величины

Дата и место не отдельные сущности, а ответы на вопросы «когда» и «где» ([Р-39](Решения.md)). Вид даты (проектирование, открытие) и роль места (адрес объекта, место рождения) — это параметры со значением-датой и значением-местом.

У объекта не одна дата: замысел, начало строительства, открытие, реконструкция, утрата приходятся на разные годы. Датировки по-прежнему можно задать списком через `PUT /entities-dates/{id}` — маршрут сохранён и переводит список в значения параметров. Виды дат берутся из `GET /parameters` (это параметры с `value_type: "date"`), словаря `date_kinds` больше нет.

- **Неизвестное остаётся пустым.** Нет сведений о месяце — месяц не указывается; нет даты вовсе — она не выдумывается.
- **Приблизительность отмечается признаком** `is_approximate`, а не сдвигом года. «Около 1930» — это `start_year: 1930, is_approximate: true`.
- **Незавершённое** отмечается `is_ongoing: true` и остаётся без конечного года.
- Год может быть отрицательным — это даты до нашей эры.
- Конец раньше начала отклоняется.

### Остальное, о чём стоит знать заранее

- **Место** — отдельная запись, привязывается с ролью: адрес объекта, место рождения, захоронение, офис организации. Одно место переиспользуется многими объектами ([Р-25](Решения.md)).
- **Метка** — слово из общего справочника. Регистр и лишние пробелы двойников не создают, решётка в базу не попадает ([Р-29](Решения.md)).
- **Изображение** хранится в медиатеке, а в тексте живёт ссылкой по идентификатору. Оригинал неизменен; экранную версию и превью делает сервер.
- **Каждое изменение создаёт версию.** Правка присылает версию, от которой началась; если материал успели изменить, придёт `409 version_conflict`, и чужая работа не затрётся.
- **Черновик не виден постороннему.** Пока материал не опубликован, карточка, текст и файлы отдаются только тем, у кого есть права.

## Вход и права

Токен выдаёт Supabase Auth, API проверяет подпись:

```
Authorization: Bearer <access_token>
```

Без токена доступно чтение опубликованного. Участник заводится при первом входе и прав не получает: роли назначает администратор.

| Право | Что открывает |
|---|---|
| `view` | Просмотр доступных материалов |
| `edit` | Правка существующих, привязка мест, файлов и меток |
| `create_delete` | Создание объектов, связей, файлов, мест |
| `publish` | Публикация своей версии |
| `review` | Рассмотрение чужих версий |
| `su` | Полный административный доступ |

`GET /me` возвращает участника и его действующие права.

## Ошибки

```json
{ "error": { "code": "version_conflict", "message": "…", "details": {}, "request_id": "…" } }
```

Код латиницей — для программы, сообщение по-русски — для человека. Коды: `validation_failed` (400), `unauthenticated` (401), `permission_denied` (403), `not_found` (404), `version_conflict` и `duplicate` (409), `payload_too_large` (413), `link_requires_justification` (422), `internal_error` (500).

## Маршруты

### Справочники и служебное

| Маршрут | Что делает |
|---|---|
| `GET /health` | Живость сервиса и задержка базы |
| `GET /capabilities` | Версия контракта, лимиты, дерево типов записей (`entity_types`) и словари: виды изображений, виды источников, роли связей, роли вложений |
| `GET /me` | Участник и его права |
| `POST /session` | Меняет токен на короткоживущую куку для показа приватных файлов в теге изображения |

Коды словарей берутся из `capabilities`, а не придумываются.

### Объекты, участники, периоды

| Маршрут | Что делает |
|---|---|
| `GET /entities?type=&q=&cursor=&limit=&archived=1` | Каталог с отбором по ветви дерева типов и поиском по названию. Архив не показывается; `archived=1` возвращает и его — для поиска убранного |
| `GET /entities?parameter=&min=&max=&sort=parameter&order=desc` | Отбор и сортировка по величине. В ответе приходит `parameter_value`; при сортировке по величине постраничный указатель не выдаётся |
| `GET /entities/{id}` | Карточка: свойства, тип и путь по дереву, показатели (включая даты и места), файлы, метки, ссылка на описание, текущая версия |
| `POST /entities` | Создание; требует `create_delete` |
| `PATCH /entities/{id}` | Правка; требует `edit` и `base_revision_id` |

```json
POST /entities
{
  "type": "architecture_object",
  "slug": "novosibirskiy-teatr-opery-i-baleta",
  "title_ru": "Новосибирский театр оперы и балета",
  "title_en": "Novosibirsk Opera and Ballet Theatre",
  "profile": { "typology": "Театр" }
}
```

Ответ: `{ "id": 17, "material_id": "…", "revision_id": "…" }`. Возвращённый `revision_id` присылается в следующей правке как `base_revision_id`.

`slug` — только строчные латинские буквы, цифры и дефис, уникален среди всех записей. Прежний адрес сохраняется, старые ссылки не ломаются.

`profile.typology` — временное поле: на следующем этапе типология станет значением параметра ([Р-38](Решения.md)).

### Параметры и показатели

| Маршрут | Что делает |
|---|---|
| `GET /parameters` | Справочник: код, название, единица, тип значения, определение, сколько раз заполнен |
| `GET /parameters/for-type/{код}` | Что подсказано этому типу: наборы его ветви сверху вниз |
| `POST /parameters`, `PATCH /parameters/{id}`, `DELETE /parameters/{id}` | Ведение справочника; требует `su`. Тип значения у заполненного параметра не меняется, заполненный параметр не удаляется |
| `GET /parameter-sets` | Наборы с составом и ветвями, к которым привязаны |
| `POST /parameter-sets`, `PUT /parameter-sets/{код}/items` | Завести набор и задать его состав целиком; требует `su` |
| `POST /parameter-sets/{код}/types`, `DELETE /parameter-sets/{код}/types/{тип}` | Привязать набор к узлу дерева и отвязать; требует `su` |
| `PUT /entities-indicators/{id}` | Показатели записи целиком; требует `edit` и создаёт версию записи |

Типы значений: `number`, `integer`, `text`, `boolean`, `option` (выбор из списка параметра), `date`, `place` (ссылка на справочник мест).

```json
PUT /entities-indicators/17
{
  "base_revision_id": "…",
  "indicators": [
    {
      "title": "По проекту",
      "is_current": true,
      "measured_year": 1931,
      "values": [
        { "parameter": "hall_capacity", "num_value": 3000 },
        { "parameter": "typology", "text_value": "Театр" },
        { "parameter": "opening", "date_start_year": 1945 },
        { "parameter": "address", "place_id": "…" }
      ]
    }
  ]
}
```

Незаполненное не пишется: величина без ответа просто отсутствует. Значение не того типа отклоняется — параметру с типом «текст» число не подойдёт.

Прежнее `profile.typology` при создании и правке записи по-прежнему принимается и ложится значением параметра `typology`.

### Датировки

```json
PUT /entities-dates/17
{ "dates": [
  { "kind": "design", "start_year": 1929 },
  { "kind": "construction_start", "start_year": 1931 },
  { "kind": "opening", "start_year": 1945, "start_month": 5, "start_day": 12 },
  { "kind": "reconstruction", "start_year": 2003, "end_year": 2005, "is_approximate": true }
] }
```

Список задаётся целиком: присланное заменяет прежнее.

### Тексты

| Маршрут | Что делает |
|---|---|
| `POST /documents` | Создание текста, при желании сразу прикреплённого к объекту |
| `GET /documents/{id}` | Текст с блоками и текущей версией |
| `PATCH /documents/{id}` | Правка; требует `base_revision_id` |

Тело — блоки BlockNote. Собственные блоки проекта:

- `entityCard` — карточка объекта отдельным блоком, `props: { entityId, occurrenceId }`;
- `entityMention` — упоминание внутри абзаца, те же свойства, но внутри `content`;
- `mediaImage` — изображение из медиатеки, `props: { assetId, caption, variant }`.

```json
POST /documents
{
  "title": "Описание: Новосибирский театр оперы и балета",
  "attach_to_entity_id": 17,
  "role": "description",
  "body": [
    { "id": "b1", "type": "heading",
      "content": [{ "type": "text", "text": "Купол и сцена", "styles": {} }] },
    { "id": "b2", "type": "paragraph",
      "content": [{ "type": "text", "text": "Зал под сводом купола.", "styles": {} }] },
    { "id": "b3", "type": "mediaImage",
      "props": { "assetId": "…", "caption": "Общий вид", "variant": "screen" } }
  ]
}
```

Сервер сам извлекает текст для поиска и указатель вхождений объектов. Ссылка на несуществующий объект отклоняется. Неизвестные типы блоков сохраняются без потери.

### Медиатека

| Маршрут | Что делает |
|---|---|
| `GET /media?q=&cursor=` | Список файлов с состоянием вариантов и метками |
| `POST /media` | Загрузка оригинала, `multipart/form-data` |
| `GET /media/{id}` | Сведения о файле |
| `PATCH /media/{id}` | Правка сведений; файл не меняется |
| `GET /media/{id}/file?variant=thumbnail\|screen\|original` | Выдача файла |
| `POST /media/attachments` | Привязка файла к объекту с ролью; файл встаёт в конец |
| `PUT /media/attachments/order` | Порядок изображений у объекта: список привязок целиком |
| `DELETE /media/attachments/{id}` | Отвязка |
| `POST /media/{id}/derivatives` | Повтор обработки после ошибки |

Поля формы загрузки: `file`, `kind` (вид изображения из словаря), `caption`, `author` (фотограф или чертёжник), `source_url`, `license`, `keywords` (через запятую — станут метками). Контрольную сумму, размеры, экранную версию и превью сервер делает сам.

Файл передаёт клиент; сервер не скачивает произвольные адреса.

### Места

| Маршрут | Что делает |
|---|---|
| `GET /places?q=` | Справочник; требует `edit` |
| `POST /places` | Создание места |
| `PATCH /places/{id}` | Правка |
| `GET /places/{id}/usage` | Где место используется |
| `POST /places/attachments` | Привязка к объекту с ролью |
| `DELETE /places/attachments/{id}` | Отвязка |

```json
POST /places/attachments
{ "entity_id": 17, "role": "address",
  "place": { "country": "Россия", "settlement": "Новосибирск",
             "street": "Красный проспект", "house": "36",
             "lat": 55.030476, "lon": 82.924856, "precision": "building" } }
```

Вместо описания места можно прислать `place_id` уже существующего. Координаты указываются парой. Пустое место не создаётся.

**Повтор адреса не заводит второе место.** Совпадение ищется без учёта регистра и лишних пробелов: «Красный проспект» и «красный  проспект » — одно место. Если такое уже есть, возвращается его идентификатор с пометкой `reused: true` и кодом 200 вместо 201; недостающие координаты при этом дописываются. На уровне базы повтор адреса запрещён.

### Публикация и рассмотрение

Каждая запись — объект, текст, файл, место, связь — имеет материал: единицу авторства, версий и состояния. Идентификатор материала возвращается при создании (`material_id`) и лежит в карточке объекта.

| Маршрут | Что делает |
|---|---|
| `GET /materials/{id}` | Состояние: черновик или опубликовано, какая версия опубликована, ход рассмотрения |
| `POST /materials/{id}/publish` | Публикация версии; требует `publish` |
| `POST /materials/{id}/submit` | Отправка версии на рассмотрение; требует `edit` |
| `POST /materials/{id}/review` | Решение по чужой версии: `approved` или `rejected`; требует `review` |
| `DELETE /materials/{id}` | Архивирование: уходит из показа, история и файлы остаются |

Архивирование затрагивает только сам материал. Описание объекта — отдельный материал, и оно архивируется отдельным вызовом. Это временное поведение: распространять архивирование на прикреплённые тексты предстоит отдельным решением.

```json
POST /materials/55dd101f-…/publish
{ "note": "первая публикация" }
```

По умолчанию публикуется последняя версия; можно указать `revision_id`. Повторная публикация той же версии отклоняется.

**Кто без права `publish`** отправляет версию через `submit`: материал при этом не меняется, читатель продолжает видеть прежнее. Обладатель `review` принимает или отклоняет; принятие означает публикацию.

Публикация объекта делает публично видимыми его карточку, датировки, места и метки. Прикреплённые файлы становятся доступны, когда опубликован их собственный материал.

## Порядок наполнения одного объекта

1. `GET /capabilities` — взять коды словарей.
2. `POST /entities` — создать объект, запомнить `id` и `revision_id`.
3. `PUT /entities-dates/{id}` — датировки, если известны.
4. `POST /places/attachments` — адрес или другое место.
5. `POST /media` — загрузить изображения, затем `POST /media/attachments` на каждое.
6. `POST /documents` с `attach_to_entity_id` — описание; изображения внутри вставляются блоком `mediaImage`.
7. `PUT /tags/entities/{id}` — метки.
8. `POST /links` — связи с другими объектами, каждая с обоснованием.
9. `POST /materials/{material_id}/publish` — публикация, если есть право `publish`.

До публикации материал остаётся черновиком и посторонним не виден.

## Чего пока нет

Спроектировано, но не реализовано; выдавать за работающее нельзя:

- история версий и восстановление прежней версии;
- пакетный импорт и проверка пакета;
- управление пользователями и ролями;
