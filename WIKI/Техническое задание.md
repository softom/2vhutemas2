# Техническое задание

Требования пользователя и проект реализации. Состояние сервера проверено 2026-09-22 ([инвентаризация](Архив/Инвентаризация%20сервера.md)); из изменений выполнено только закрытие прав записи для `anon` (решение [Р-05](Архив/Архив%20решений.md)). Новые таблицы и сервисы не создавались.

## Пользователи и Telegram

- Студенты — обычные пользователи. Отдельной роли доступа «студент» нет.
- Заводить пользователей из существующей ведомости, сохраняя связь с записью студента и результатами сессии. Повторный импорт не создаёт дубли.
- Принадлежность аккаунта подтверждается через Telegram-бота. Имя или username не служат подтверждением.
- Переиспользовать `students.student_account` и коды привязки после сверки с сервером. До подтверждения не предоставлять права изменения материалов.
- Предлагаемый процесс: адресное приглашение/одноразовый код → подтверждение в Telegram → атомарная привязка Telegram ID → активация. Код ограничен по времени, повторно не используется. Конфликт привязки разрешает администратор; автоматическая перезапись запрещена.
- Первоначальные права назначаются независимо от статуса студента. Конкретный набор по умолчанию и восстановление Telegram-привязки ещё предстоит определить.

**Уточнение 2026-10-01 ([Р-87](Решения.md)), по итогам обсуждения со студентами:**

1. Студент регистрируется сам, без приглашения от администратора. Способы входа: Telegram-бот и внешняя регистрация через Yandex ID или по телефону/почте. Это заменяет требование подтверждать аккаунт только через Telegram (строки выше остаются как история).
2. Личный кабинет есть у каждого пользователя, а не только у студентов.
3. Кроме уровней прав (reader … su) доступ даётся **пообъектно** (раздел «Права»).

Остаётся решить:
- Как зарегистрированный связывается со своей записью в ведомости. Предложение: через бота по Telegram ID. Бот получает ID от самого Telegram, и он совпадает с `students.student.tg_id`, который уже заполнен у 37 студентов из 41. Телефонов в ведомости нет ни одного, так что сверка по телефону пока невозможна. Вошедшие через Yandex ID или телефон/почту связываются с ведомостью привязкой Telegram в кабинете либо решением администратора. Конфликт — администратору, автоматической перезаписи нет.
- Yandex ID штатно в Supabase Auth не поддерживается. Нужно проверить, можно ли подключить его своим OIDC/OAuth-провайдером, или сделать вход через наш API.
- Какие права у только что зарегистрированного. Предложение: просмотр и создание своих объектов; чужие объекты только по доверию.

**Сверка ведомости на сервере 2026-10-01** (только чтение, личные данные не выводились):
- В `students` 22 таблицы: 41 студент, у 37 есть `tg_id`, телефонов 0, `access_token` у одного. `student_account` и `link_code` пусты: ни один студент к аккаунту не привязан. В `auth.users` 3 аккаунта, в `app.contributors` 4 участника, активных назначений ролей 2, привязок Telegram 0.
- RLS включён на всех таблицах, но политика `auth_all` (`true`, все действия) по-прежнему открыта роли `authenticated`. У этой роли есть SELECT/INSERT/UPDATE/DELETE на `student` (с `access_token`), `student_account`, `link_code`, `profile`, `work*`, `work_extraction` и **`staff`**. Любой вошедший может, например, записать себя в `staff` и стать преподавателем для функций `_is_teacher`. Сами оценки (`student_grade`, `submission`) роли `authenticated` не выданы.
- Снаружи схема сейчас недоступна: PostgREST отдаёт только `public,storage,v2`, регистрация в Supabase Auth выключена (`GOTRUE_DISABLE_SIGNUP=true`), внешних провайдеров нет. Поэтому до самостоятельной регистрации студентов нужно отозвать `auth_all` и права `authenticated` на `students` и оставить доступ только нашему API по правилам «своё — своему». При включении регистрации по почте учесть, что включено `GOTRUE_MAILER_AUTOCONFIRM=true`: почта без подтверждения подтверждением не является.
- Попутно: схема `v2` всё ещё открыта в PostgREST, хотя прежний план предлагал её закрыть.

Предложение по кабинету, ждёт согласования: профиль и подпись, способы входа и их подтверждение, действующие права (общие и по объектам), «мои объекты» (свои и доверенные), заявки на объекты, мои черновики и версии на рассмотрении. Студент видит свои результаты сессии и только свои.

## Права

Принято пользователем: `view` — просмотр, `edit` — редактирование, `create_delete` — единое неразделимое право создания и удаления, `su` — superuser. **Уточнение 2026-09-22 (см. [Решение Р-04](Решения.md)):** публикация отделена от редактирования — `publish` позволяет опубликовать версию самостоятельно, `review` позволяет рассматривать чужие предложения. Пользователь без `publish` отправляет версию на рассмотрение, опубликованный материал при этом не меняется. Роли объединяют разрешения; отдельные create и delete не назначаются. su — полный административный доступ приложения с аудитом, не роль суперпользователя PostgreSQL.

Авторство материала, статус в ведомости и роль в культурной связи не определяют права доступа. Управление назначениями — отдельная административная операция. Прежняя предложенная матрица author/editor/curator заменена этой моделью; обязательная публикация через куратора не утверждена.

**Пообъектный доступ (Р-87, 2026-10-01).** Глобальная роль (reader … su) действует на все материалы. Студент правит **свои объекты** (созданные им) и **объекты, доверенные ему для правки суперпользователем**. Доверие выдаётся двумя путями: студент подаёт заявку, а su её одобряет, или su назначает сам. У одного объекта может быть несколько участников. Статус в ведомости по-прежнему прав не даёт; права даёт назначение «участник ↔ объект». Назначение, отзыв и решение по заявке сохраняются в истории.

Предложение по модели, ждёт согласования (правило 14): новую сущность не заводить, добавить к `user_roles` необязательную область `entity_id`. Пустая область — роль на всё, заполненная — роль только на этот объект; несколько участников на объект допускаются. Создатель объекта получает назначение на него при создании. Для заявок нужно состояние назначения (заявка → одобрено/отклонено) либо отдельная таблица заявок, это тоже на согласование.

Ещё не решено: распространяется ли доверие на связи, изображения и тексты объекта; может ли студент публиковать доверенный объект сам или только через рассмотрение (`publish`/`review`); снимает ли доверие редактор или только su.

Проверка прав выполняется на сервере по ресурсу. Доступ к материалам не даёт доступа к чужим оценкам. Публичный просмотр опубликованных материалов сохраняется. Порядок публикации определён решением [Р-04](Решения.md). Состав начальных ролей и область действия прав предстоит согласовать.

Все изменения и авторские подписи сохраняются. Предлагаемая семантика удаления в интерфейсе — архивирование с сохранением истории; физическое удаление остаётся отдельной служебной процедурой.

## Хранение изображений

Искать изображения объектов в хорошем доступном разрешении. Для каждого изображения хранить:

| Вариант | Назначение | Требование |
|---|---|---|
| `original` | Архив и детали | Исходные байты, разрешение и формат без перезаписи |
| `screen` | Экранный просмотр | Производная из оригинала с сохранением пропорций |
| `thumbnail` | Карточки и списки | Компактная производная для быстрой загрузки |

Размеры и прочие настройки вынесены в [Параметры проекта](Параметры%20проекта.md) и проект YAML; значения пока проектные. Не увеличивать маленькие оригиналы; учитывать ориентацию, цветовой профиль и прозрачность. Кадрирование в композиции не меняет оригинал.

Файлы — в существующем файловом контуре медиасервиса; БД — реестр и метаданные. Точный корневой путь и состояние сервиса сверяются перед реализацией. Новый бакет или инфраструктура этим требованием не вводятся.

Для каждого варианта сохранять тип, ключ хранения, MIME, байты, ширину/высоту, SHA-256, статус готовности, версию и параметры обработки, время создания. Для изображения — источник, автора/кредит и условия использования, если известны.

Процесс: оригинал → проверка/регистрация → генерация screen и thumbnail → проверка готовности. Ошибки сохраняются и допускают повтор обработки. Списки используют thumbnail, просмотр — screen, оригинал открывается отдельным действием при наличии доступа.

Все варианты наследуют доступ изображения. Резервные копии включают БД и оригиналы; производные воспроизводимы по сохранённым настройкам. Замена или архивирование карточки не удаляет файлы, используемые историей документов.

## Лекции и самостоятельные статьи

**Требование 2026-09-22:** автор собирает объекты из БД в самостоятельную лекцию, задаёт их порядок и пояснения. Студенты читают лекцию и переходят к подробному изучению объектов. Статья/лекция имеет собственные название, адрес, авторство и версии и не обязана быть вложением к объекту.

- В BlockNote доступны вставка ссылки в тексте и блок-карточка существующей сущности через поиск по базе. Новая копия объекта при вставке не создаётся.
- Карточки перемещаются вместе с блоками лекции; между ними можно добавлять текст, иллюстрации, вопросы, заголовки и сравнения. Порядок лекции независим от исторических дат и общего sort_order объекта.
- Один объект может встречаться в нескольких лекциях и несколько раз в одной. Пояснение конкретного появления принадлежит лекции и не заменяет описание объекта.
- У сущности есть устойчивый адрес по ID; slug используется для читаемости и может изменяться без поломки ссылок. У лекции также отдельный устойчивый адрес.
- Карточка открывает подробности объекта, его авторов, медиа, связи и источники. Возврат восстанавливает место в лекции. Отдельный список объектов лекции строится по порядку появления карточек.
- У объекта показываются доступные читателю лекции, где он упомянут. Черновики и закрытые материалы через обратные ссылки не раскрываются.
- Удаление карточки из лекции не удаляет объект из базы. Архивирование объекта не должно оставлять необъяснимую пустоту: показывается отметка недоступности без раскрытия закрытых данных.
- Предлагаемый режим по умолчанию: ссылка открывает текущую опубликованную карточку объекта. Для неизменяемой учебной подборки можно явно закрепить версию объекта; выбор отражается в интерфейсе.
- Сохранение/публикация проверяет ссылки и права. Правка лекции создаёт её версию, не меняя объекты и чужие лекции.

Подробный план работ и критерии приёмки — [План реализации](План%20реализации.md).

### Зависимости этапов

Таблица пользователя сохраняется как основной план экранов. Этап 1 — главная, каталог и карточки, редактор, медиатека и импорт; этап 2 — связи и лекции; этап 3 — экраны истории, аккаунта и управления пользователями; этап 4 — таймлайн.

API, проверка доступа существующего редактора, запись версий/авторства и BackUp нужны с этапа 1. На этапе 3 добавляются их полноценные пользовательские экраны и массовое подключение через ведомость/Telegram. Ссылки на ещё не реализованные лекции, историю и новый таймлайн на ранних экранах не ведут в пустые страницы; пункты включаются по готовности. Старая версия сайта остаётся отдельной до переключения.

## API и автоматизированное наполнение

API закладывается с первой версии: все основные действия над объектами, связями, лекциями и медиа доступны через документированный контракт. Веб-интерфейс, бот и навык используют общие проверки прав, версионирование и правила данных. Подробности — [API проекта](API.md).

Для быстрого наполнения создаётся проектный навык 2vhutemas-content: подготовка материалов, поиск дублей, пакетная проверка, создание зависимых записей, сборка лекции и проверка результата. Предусмотреть dry-run, идемпотентность, частичные ошибки и отчёт. Публикация и выдача прав не подразумеваются автоматически при импорте.

Сейчас подготовлен исходник навыка, а API только спроектирован. Реальный импорт станет доступен после реализации и проверки контракта; навык не должен обходить его прямой записью в БД.

## Проверка результата

- Повторный импорт ведомости не создаёт второй аккаунт; истёкший или использованный код не принимается.
- Одинаковые разрешения дают одинаковые возможности независимо от статуса студента; каждый запрет проверяется также прямым запросом API.
- Оригинал совпадает по SHA-256 с исходником. Две производные имеют правильные размеры и состояния; ошибка генерации допускает повтор.
- Приватность проверяется для всех вариантов. Восстановление БД и оригиналов из резервной копии проверено.
- Замена изображения сохраняет доступность старых файлов для истории материалов.
- Автор собирает три существующих объекта в лекцию, меняет порядок и сохраняет. После открытия порядок и пояснения воспроизводятся; переход в объект и возврат сохраняют место чтения.
- Повторное использование объекта не создаёт дубль; удаление вхождения не удаляет карточку. Обратные ссылки учитывают права и опубликованную версию лекции.
- Правка пользователя без `publish` не изменяет то, что видит читатель, до решения о публикации; пользователь с `publish` публикует сам. Отклонение предложения сохраняет объяснение и авторство.
