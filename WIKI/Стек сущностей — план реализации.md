# Стек сущностей — план реализации

2026-11-11. Пользователь поручил реализовать самостоятельный стек досье. Документ — конкретное предложение физического хранения для согласования по правилу 14; миграций и новых таблиц пока нет.

## Предлагаемое хранение: три таблицы

| Таблица | Поля и связи |
|---|---|
| app.entity_intake | id UUID; title; description; status; reason; target_entity_id → entities.id (существующий bigint UID); version; created_by/updated_by → contributors.id; created_at/updated_at |
| app.entity_intake_sources | id UUID; intake_id → entity_intake.id; url; title; description; publisher; author; published_at (дата); created_at/updated_at |
| app.entity_intake_media | id UUID; source_id → entity_intake_sources.id; url; media_entity_id → entities.id; kind; caption; author; status (link / stored / error); error; created_at/updated_at |

Названия/URL не являются внутренними FK. Досье объединяет источники через intake_id; медиа принадлежит конкретному источнику через source_id. Полученный файл используется через существующую медиатеку и её UID, а не второй файловый склад. Состояние stored допускается только при проверенной записи медиа; одна внешняя ссылка означает link.

Статусы задания: proposed, reviewing, needs_info, ready, done, rejected. Причина обязательна для needs_info/rejected. Готовность требует содержательного источника; done — существующей целевой сущности и подтверждения редактора о завершении переноса. Внесение выполняется через действующий редактор сущности, без автоматической публикации. Досье и источники после завершения сохраняются.

История изменения — штатный аудит проекта в транзакции с contributor UID; optimistic version защищает от потери параллельных правок. Доступ только edit/su; гости и публичные страницы стека не видят. Никаких новых прав или типов сущностей не требуется. Новые данные входят в полный backup app; до миграции проверяется дамп.

## Первая реализация

1. Самостоятельная страница стека с фильтром статуса, поиском и страницами по 30 досье.
2. Создание и редактирование досье; список источников с отдельными описаниями; медиа с происхождением, подписями, ссылкой/UID и состоянием.
3. Ручной вход; из кандидата новостей — открытие заполненного досье с доступными источниками, описанием и медиа. Выбор существующего досье позволяет добавить источник без второй копии задания. Отбор в новости от этого не меняется.
4. Сопоставление с существующей сущностью, открытие её редактора, проверяемое завершение задания. Создание новой сущности — штатный редактор, затем привязка UID.
5. Проверки прав, валидации URL/UID, конфликтов версий, сохранности источников/медиа и повторной отправки; штатный smoke и браузерные сценарии.

Автоматическое распознавание авторов/типологии, сбор содержимого произвольных сайтов, скачивание внешних медиа и автоматическое применение связей — дальнейшая работа блока 2.2.1, не имитация в первом выпуске стека. Интерфейс честно показывает доступные данные и пробелы. Существующий контент/права/настройки и пользовательские правки этапов сохраняются.


## Контракт интерфейса и API

Самостоятельный адрес `/entity-intake`, пункт «Стек сущностей» в меню для редакторов. Список по 30 строк, без постоянной перерисовки всего массива: название, статус, число источников/медиа, целевая сущность, дата правки. Карточка: описание задания; сопоставление; вкладки/раскрываемые источники с описанием и своими медиа; результат проверки и действия со статусом.

Предлагаемые маршруты: GET/POST `/api/v1/entity-intake`; GET/PUT `/api/v1/entity-intake/:uuid`. PUT требует номер версии и передаёт целое досье с устойчивыми UID источников/медиа; сервер проверяет принадлежность каждого UID этому досье. Повтор POST с тем же клиентским UUID не создаёт второй объект. Удаление досье не входит в первую реализацию: отклонение сохраняет материалы и причину. Удаление/изменение источника сохраняется в истории аудита.

При передаче новости не переносим только заголовок: открываем форму с источниками кандидата и повторов, доступными описаниями/медиа; отсутствие собранного текста или файла явно видно. Редактор выбирает новое либо существующее досье и подтверждает сохранение. Внесение в каталог не меняет verdict новости и очередь публикации.

Проверка на сервере должна включать сохранение и повторное чтение досье с двумя источниками и медиа, отсутствие доступа у гостя, отказ на чужой UID источника/медиа, конфликт версии, причину отказа и запрет done без действительной целевой записи. Проверка BackUp должна охватывать новые таблицы и файлы штатной медиатеки.
