## Локализация и следующий шаг

Обработчик api/src/routes/entities.ts строит один SQL с read_entities, параметрическими фильтрами, сортировкой, cover_asset и compact_json. Это кандидат для EXPLAIN ANALYZE после получения точных параметров проблемного GET; тяжесть отдельных функций пока гипотеза.

Для вошедшего пользователя publicPage.ts последовательно ожидает site-header → session → card; API предварительно ждёт supabase.auth.getSession(). Это дополнительный возможный источник ожидания, но текущие измерения его причиной не доказали.

Запрошены адрес проблемной страницы и описание симптома. Следующий шаг: воспроизвести конкретное действие, получить параметры и тайминг запроса в браузере, затем проверить SQL-план/ожидания БД. Полное время браузерной отрисовки и пользовательская сессия не измерены. Production, БД, настройки и пользовательские файлы не менялись; backup/push не выполнялись.
## Уточнение по снимку пользователя: обложки «Проектов»

Пользователь уточнил: при открытии «Проектов» загружается менее 10% обложек; на снимке видны штатные заглушки «без изображения».

Причина подтверждена публичным GET /api/v1/entities?scope=objects&limit=24 и SELECT в транзакции READ ONLY:

- Из первых 24 записей 8 имеют публичную обложку, 16 возвращают cover_asset_id=null и compact.thumbnail.asset=null.
- У 15 из этих 16 обложка существует в рабочем представлении app.cover_asset(id,true). Связи «иллюстрация» опубликованы, но сами записи изображений имеют status=draft и published_revision_id IS NULL. Для гостя app.cover_asset(id,false) закономерно возвращает NULL.
- Например, Friendship Centre (3134): 5 опубликованных связей к черновым изображениям; Torres de Colón (3108): 9; Nakagin (3090): 2. У мавзолея (3121) и конкурса Powerhouse (2963) опубликованы и связи, и изображения — обложки видны, как на снимке.
- У конкурса Норвежской оперы (2668) связей иллюстраций нет вообще.

Это не ожидание скачивания: pages.ts при отсутствии compactPicture сразу формирует card-no-cover с текстом «без изображения», без запроса картинки. Повторная загрузка и ожидание не устранят эти заглушки. Выбросы длительности /entities из первой части отчёта — отдельное наблюдение и не объясняют отсутствие обложек на этом снимке.

app.cover_asset в 0026_one_model.sql допускает гостю только опубликованные изображения и связи. Ослаблять эту проверку нельзя: это раскрыло бы черновики. Для исправления требуется штатная публикация выбранных изображений с сохранением версий/авторства и проверка процесса, который публикует проект и связь, оставляя изображение черновиком. По текущему чтению не доказано, какая конкретная операция создала это расхождение; автоматически публиковать весь набор черновых материалов не следует. В рамках запроса диагностики данные/права/код production не изменялись.
## Исправление вывода после второго снимка пользователя

Пользователь показал ту же страницу через ~15 секунд: появился аккаунт и все ожидаемые обложки. Прежний вывод «ожидание не поможет» неверен для вошедшего редактора; рекомендация публикации изображений не является решением заявленной задержки. Предыдущий раздел описывает только гостевое состояние.

Подтверждённая цепочка по коду:
1. Сервер отдаёт публичную первую страницу (catalog-initial): черновые изображения скрыты.
2. main.tsx загружает appMount для каталога; Catalog.tsx начинает с публичных данных и затем запрашивает api.entities с type=what, scope=objects и текущим токеном (после debounce 250 мс).
3. api.ts перед запросом ждёт supabase.auth.getSession(). App.tsx отдельно получает site-header и открывает медиасессию для приватных изображений.
4. Ответ редакторского списка заменяет items; рабочие изображения становятся доступны, что соответствует второму снимку.

Следовательно, наблюдаемое ожидание относится к получению редакторского состояния каталога, а не к отсутствующим файлам. Черновые изображения объясняют различие двух снимков, но сами по себе не объясняют длительность 15 секунд. Публиковать их ради ускорения или ослаблять права не требуется.

Дополнительная проверка SQL из entities.ts в production READ ONLY, без вывода содержимого карточек: подставленные параметры редакторского каталога — 175 мс; PREPARE с индивидуальным планом — 157 мс, с принудительно общим — 249 мс. Это диагностическая роль postgres, не реальный HTTP-запрос пользовательской сессии; SET ROLE app_api недоступен. Серверные настройки/права не менялись. Поэтому 13–14-секундные запросы из журнала остаются свидетельством эпизодической задержки, но совпадение с конкретной загрузкой пользователя не доказано.

Точный вклад ожидания сессии, передачи/выполнения клиента, списка API и медиасессии ещё требует браузерного тайминга именно авторизованной загрузки. Нельзя объявлять корневую причину длительности установленной только по двум снимкам. Код и данные production не менялись.
