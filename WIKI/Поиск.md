# Поиск

Решение — [Р-109](Решения.md). Связано: [Схема данных](Схема%20данных.md), [API](API.md), [Робот новостей](Новости%20—%20робот,%20цепочка%20и%20промпты.md), [BackUp](BackUp.md).

## Что есть сейчас (сверено с кодом 2026-10-05)

- `GET /entities?q=` — подстрока `ILIKE '%q%'` по `title_ru`/`title_en` (`api/src/routes/entities.ts`). `title_original`, сведения и текст записи не ищутся; нет морфологии, ранжирования и индекса.
- `GET /media`, `/places` — `ILIKE` по JSON записи, приведённому к строке; `/tags` — по названию метки.
- `documents.search_vector` (tsvector, русский) — только у прежних текстов, никем не читается.
- Текст записи — блоки BlockNote в `indicator_values.blocks_value`; плоский текст умеет извлекать только `extractText` в API (`api/src/routes/documents.ts`).
- Робот склеивает издания одной истории по `story_key`, который придумывает LLM; поиск проекта и автора для Р-106 — точное совпадение названия.

## Принято (Р-109)

1. **Векторы — в pgvector, в той же БД `supa_db`.** Отдельной векторной БД нет: одна копия BackUp, права через `read_entities`, поиск — один SQL-запрос. На сервере pgvector 0.8.0 уже используется проектом Social View (их WIKI, 2026-07-18); включено ли расширение для схемы `app` — проверить перед миграцией.
2. **Поиск гибридный.** Полнотекстовый (`tsvector`, русская конфигурация) находит точные имена и названия, векторный — смысл; списки сливаются по местам (RRF).
3. **Поиск различает, где найдено: Название · Сведения · Текст.** Каждая запись индексируется кусками трёх видов:
   - **Название** — название, другие названия (ru, оригинал, en, la), тип;
   - **Сведения** — значения параметров словами («Пролёт: 43 м», «Адрес: Новосибирск…», даты, варианты), у изображения — подпись, описание, описание для незрячих;
   - **Текст** — текст записи, разбитый по заголовкам на куски примерно по 500 токенов.
   В выдаче видно, в чём совпало, и фрагмент; вес вида настраивается (название сильнее текста). Можно искать только в одном виде.

## Принято 2026-10-05 (второй шаг Р-109)

- **Модель — сразу `openai/text-embedding-3-large`, 1536 измерений.** Пользователь: «база не большая… если потеряем смысл, просто перебьём всю базу другой моделью». Замер не проводим. Модель — настройка API `SEARCH_EMBED_MODEL`; смена пересчитывает все векторы.
- **Таблица кусков `app.search_chunks` — «Утверждаю».**
- **Порядок:** сначала индекс и векторы, потом окно поиска и API.

## Как устроено (миграция 0033, код API)

**Таблица `app.search_chunks`** — служебный склад, как `document_entity_refs`: производные данные, полностью воспроизводимые из версий.

| Поле | Что |
|---|---|
| `entity_id`, `revision_id` | запись и версия, из снимка которой собран кусок |
| `scope` | `published` — видно гостю, `working` — редакторам |
| `kind` | `title` / `params` / `text` |
| `chunk_no`, `block_id` | порядок и первый блок текста — для перехода к месту |
| `content` | плоский текст куска |
| `tsv` | вычисляемый `tsvector('russian')` с весом по виду: A, B, C |
| `model`, `embedding` | модель и вектор `vector(1536)`, индекс HNSW по косинусу |
| `content_sha256` | хеш того, что ушло в модель: одинаковый текст эмбеддится один раз |

**Куски.** Собираются из снимка версии (`revisions.snapshot`), а не из рабочих таблиц:
- название — все названия, тип, метки;
- сведения — `app.search_params_text`: «Параметр: значение единица — примечание», варианты, даты, места названием;
- текст — блоки BlockNote, разрезанные по заголовкам и до ~1800 знаков; кусок помнит первый блок.

В модель кусок сведений или текста уходит вместе с названием записи — иначе абзац не знает, о каком он здании.

**Индексатор** работает фоном внутри API (`api/src/lib/search.ts`), раз в 15 с:
1. убирает куски снятого с публикации и архивного (`app.search_prune`);
2. находит записи, у которых указатель версии сдвинулся (`app.search_stale`), и пересобирает их куски (`app.search_put`; вектор переносится с куска с тем же хешем);
3. досчитывает векторы пачками по 64 через Polza.AI (`/embeddings`, `dimensions=1536`).

Маршруты правки и публикации об индексе не знают: сохранение не ждёт модель и не падает из-за неё. Без ключа `POLZA_API_KEY` индекс строится, поиск — только по словам. Сбой пишется в журнал API уровнем `error` и виден в `GET /search/status`; уведомления в Telegram у API пока нет (правило 13 — открыто).

**Запрос** (`app.search`): два списка по 100 кусков — полнотекстовый (слова запроса префиксами, все обязательны) и векторный (косинус) — сливаются по местам (RRF, k = 60) с весом вида: название 1,0, сведения 0,7, текст 0,5. У записи — лучший кусок: где найдено и фрагмент с выделенными словами. Маршруты — [API](API.md), раздел «Поиск».

**Стоимость.** text-embedding-3-large через Polza — 13,54 ₽ за 1 млн токенов (выверка Social View); весь нынешний корпус — порядка рублей, полный пересчёт при смене модели — десятки рублей.

## Модель эмбеддингов — опыт Social View

Прочитано в WIKI Social View (`_WIKI_OLD/Семантический пилот — результаты (2026-07-18).md`, «Ловля смыслов в векторном поле — методы», журнал решений), тот же шлюз Polza.AI и тот же сервер:

- Основная модель там — `qwen/qwen3-embedding-8b`, хранят 1536 измерений (обрезка Matryoshka через `dimensions`). Выбрана как «лучший русский» и в 13 раз дешевле: 1,04 ₽ против 13,54 ₽ за 1 млн токенов у `openai/text-embedding-3-large`. Решающим был масштаб — миллионы сообщений.
- Поправка пользователя 2026-07-18: qwen «упускает нюанс на тонких интентах», поэтому для выбранных городов держат вторую модель `text-embedding-3-large` @1536 в той же таблице, ключ (запись, модель).
- qwen асимметричен: запрос обязан нести префикс `Instruct: …\nQuery: <текст>`, документы — без него; без префикса поиск деградирует. 3-large симметричен.
- Итоговой численной сверки qwen и 3-large в их WIKI нет — помечена «будет дополнено».

**Для нас** (до решения пользователя) корпус мал: 5000 записей × ~10 кусков ≈ 2–5 млн токенов, то есть десятки рублей на полный пересчёт даже у 3-large. Довод цены отпадает, остаётся качество. Предложение: короткий замер на наших данных — 30–50 запросов с правильными ответами (русские и английские названия, имена, смысловые запросы), `text-embedding-3-large` против `qwen3-embedding-8b`, обе @1536, мера — попадание в первую десятку. По умолчанию, если замер не нужен, — `text-embedding-3-large` @1536.

Индекс: при таком объёме точный косинус — миллисекунды; HNSW — когда записей станет больше.
