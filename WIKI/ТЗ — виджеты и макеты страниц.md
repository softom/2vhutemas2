# ТЗ — виджеты и макеты страниц

19 ноября 2026 · Проект к согласованию. Основание — решение о виджетах карточки d1465e8 и последующее обсуждение универсального виджета, слота и типа страницы. Документ задаёт целевую модель и порядок перехода. Фактическая схема БД описана в [[Схема данных]], действующий механизм карточки — в [[Виджеты карточки — контракт]], первоначальное предложение — в [[Виджеты — проект схемы данных]].

## 1. Цель и результат

Собирать страницы из собственных компонентов проекта. Автор выбирает, что показать и в каком оформлении. Один зарегистрированный виджет можно использовать на карточке, на обзорной странице и внутри Мультитекста. Каждый виджет выполняет одну задачу. Другое содержательное представление получает собственное определение; тональность и оформление могут быть вариантами одного виджета.

Результат перехода — каталог виджетов, страницы с названием и описанием, редактируемые макеты, серверное отображение страниц по макету и вставка в редакторе Мультитекста. Мини-игры входят в каталог на общих основаниях. Существующие URL, тексты, версии, подписи, источники, пользовательские настройки и права должны пережить переход.

## 2. Вызов виджета

Входные данные — UID показываемой сущности и необязательный вариант дизайна. Если по смыслу конкретному виджету сущность не нужна, его можно вызвать без UID. При пропущенном дизайне используется основной вариант. Виджет не получает как обязательный аргумент страницу, из которой его вызвали.

Каталог связывает UID с доверенной реализацией в коде. Реализация объявляет название для использования в редакторе, допустимые размеры, варианты дизайна и требования к входу. В БД хранится редактируемое название каталога; в коде достаточно исходного названия для регистрации. Разрешения на источники для каждого виджета не настраиваются. Компонент сам читает нужные данные через существующие механизмы видимости. Превью и публичный просмотр используют соответствующие доступные версии. Интерактивное поведение подключается к конкретному экземпляру, включая случай двух одинаковых игр в одном документе.

## 3. Структура БД

Имена ниже — целевые имена таблиц схемы app. Новые PK — uuid. Внешние ключи имеют тип PK соответствующей таблицы. У существующей сущности entities.id тип bigint. Название страницы, название виджета, слаг и имя реализации не используются для связей между записями.

| Таблица | Поля и ключи | Назначение |
|---|---|---|
| pages | id UUID PK, name text NOT NULL, description text NULL, current_layout_id UUID NULL FK → layouts.id | Страницы сайта — самостоятельная сущность со своим названием и описанием. current_layout_id — действующая версия страницы: макет, по которому страница выводится сейчас. Страницу открывает пункт меню или переход по ссылке. Примеры — карточка сущности, «Проекты», «Авторы», «Новости». Тип сущности по-прежнему задаёт entity_types. |
| widgets | id UUID PK, name text NOT NULL, renderer_key text UNIQUE NOT NULL | База виджетов для обеих сред вставки. renderer_key выбирает реализацию из кода. Переименование для редактора сохраняет UID. |
| layouts | id UUID PK, page_id UUID FK → pages.id, name text NOT NULL | Именованный макет одной страницы. Макет и есть версия страницы — один вариант её дизайна. Одна страница может иметь несколько макетов: действующий, прежние и пробные. Название и описание страницы в layouts не дублируются. |
| page_layout | id UUID PK, layout_id UUID FK → layouts.id, widget_id UUID FK → widgets.id, sort_order integer, row_start integer, column_start integer, row_span integer, column_span integer, design text NULL | Одна строка — один слот и занимающий его виджет. sort_order задаёт порядок чтения и заполнения. Геометрия относится к одному образцу сетки. design — вариант реализации, проверяемый при сохранении. |
| type_presentations (расширение) | layout_id UUID NULL FK → layouts.id | Для режима card выбирается макет карточки для данного типа сущности. Если макет у типа и его предков не задан, действует pages.current_layout_id страницы карточки. Макет ищется отдельно от остальных настроек представления: берётся ближайший вверх по дереву типов тип с непустым layout_id. Остальные настройки наследуются как сейчас. compact и editor продолжают использовать действующую схему. |

Обязательны все поля слота, кроме design. Координаты начинаются с 1. Ширина и высота положительны; column_start + column_span − 1 ≤ 3. Внутри макета порядок уникален, прямоугольники не пересекаются. Сохранение перестановки проверяет всю итоговую композицию одной транзакцией. Два одновременных сохранения не должны молча затереть друг друга. Повтор одного widget_id в разных слотах разрешён. Размер проверяется по контракту выбранного виджета.

**Страницы и меню.** Меню сайта открывает разные страницы. Страница — отдельная запись таблицы pages: у неё своё название и описание; эти свойства принадлежат странице, а не макету, поэтому не хранятся столбцом в layouts. Макет отвечает только на вопрос, как страница собрана из виджетов, и ссылается на свою страницу по UID. Пункт меню ссылается на страницу также по UID, а не по названию или адресу. Само меню остаётся общим элементом `siteHeader.ts` (Р-75); перенос состава меню в БД этим ТЗ не вводится. Карточка сущности — одна страница, которая показывает разные сущности по их UID. Материалы раздела «О проекте» остаются обычными записями ветви «Страницы проекта» (Р-72) и выводятся страницей карточки.

**Версия страницы.** Версия страницы — это её макет, то есть один вариант дизайна. Сценарий, ради которого версии введены: дизайн страницы поменяли, попробовали, увидели, что страница не складывается, и вернулись к предыдущему дизайну. Новый дизайн создаётся новым макетом той же страницы (копией действующего), прежний макет при этом не изменяется и не удаляется. Действующую версию указывает pages.current_layout_id; для карточки отдельного типа сущности — type_presentations.layout_id. Смена дизайна и возврат к предыдущему — это переключение указателя на другой макет той же страницы одной транзакцией, без выкладки кода и без переноса данных. Указатель может ссылаться только на макет своей страницы. Отдельного поля с номером или текстом версии у страницы нет.

**Конкретная страница и макет.** Для карточки назначение хранится в type_presentations, для остальных страниц — в pages.current_layout_id. Для существующих программных маршрутов разделов предлагается на первом этапе оставить владельцем выборки сам раздел: он задаёт фильтр, сортировку и UID своей страницы в своей конфигурации, а действующий макет берётся из pages. Так возврат к прежнему дизайну раздела не требует выкладки кода. pages хранит страницы сайта, а не показываемые ими сущности и не выборки разделов. Размещение фильтра у раздела уточняет ранний вариант из проекта схемы.

**Один источник раскладки карточки.** Раскладку карточки типа задаёт ровно один механизм. Если у типа есть макет, свой или унаследованный, карточка строится только по макету; прежнее settings.card_widgets не участвует в рендеринге. Внутри единственного слота «Параметры» продолжают действовать состав и порядок наборов из type_presentation_items и сторона из parameter_sets.card_side. Если макета нет, карточка строится только по старому механизму. Смешанного вывода нет. На время перехода pages.current_layout_id страницы карточки остаётся пустым, поэтому типы переводятся на макет по одному. Старые настройки не удаляются до этапа 7 и служат для возврата. Макет отвечает за состав виджетов и их место на странице. type_presentation_items по-прежнему задаёт состав и порядок элементов внутри виджета. В макет переносится расположение секций и дополнительных виджетов. Наличие style_solutions или area_program у типа задаёт слот параметров слева шириной две колонки, в остальных случаях — справа шириной одну колонку.

**Версии и ссылки.** Правка действующего макета сразу меняет страницу, поэтому действующий макет не правится: изменённый дизайн создаётся копией, проверяется в превью и включается атомарным переключением указателя. Прежний макет остаётся версией страницы и доступен для возврата; макет, на который указывала страница или тип, нельзя физически удалять. Каждое переключение фиксируется в аудите с автором, прежним и новым макетом, чтобы было видно, к какой версии возвращаться. Изменения каталога, макетов и назначений фиксируются с автором в действующем порядке аудита. Используемые определения нельзя физически удалять, в том числе при наличии вставок в исторических версиях Мультитекста. До реализации надёжной проверки таких ссылок каталог сохраняет определения.

## 4. Заполнение страницы

Карточка передаёт один UID своим слотам. Страница раздела формирует упорядоченную выборку. Для повторяемой части макета предусмотрены два режима.

- **Блок на одну запись.** Для каждой записи выборки страница один раз проходит блок от отметки начала до отметки конца. Все виджеты внутри этих границ получают один и тот же UID текущего проекта или автора. Переход к следующей записи происходит после конца блока. Слоты вне блока выводятся один раз за страницу.
- **Журнальный рисунок.** Каждый следующий слот рисунка получает UID очередной записи. После последнего слота рисунок начинается снова со следующей записи выборки.

Фильтрация по видимости выполняется до заполнения. Чтобы при равенстве основного значения порядок воспроизводился, последним критерием сортировки служит UID. В БД хранятся слоты одного образца. Фактические повторы и карточки текущей выдачи строятся при чтении.

**Полный макет и пустые виджеты.** Макет описывает полный дизайн страницы: на нём расположены все виджеты, которые страница может показать. Прежнее правило автоматического показа прикреплённого набора параметров (`parameter_sets`, включая `result_kind = relations`) преобразуется в общее правило: виджет выводится, если он стоит в макете (`page_layout`) и у него есть что показать. Виджет без данных освобождает своё место. Порядок вывода такой:

1. Сервер один раз отрисовывает виджеты макета. Пустой результат означает, что виджету место не нужно; отдельного опроса виджетов нет.
2. Гостю пустой слот не выводится.
3. Строка сетки, в которой не осталось ни одного слота, удаляется на сервере, нижние строки поднимаются.
4. Если в строке пуста только часть слотов, оставшиеся виджеты сохраняют свои колонки: соседи не расширяются и не переезжают.
5. Высоту строк определяет браузер по содержимому.
6. Редактор в превью видит все слоты макета; пустые показаны с явным пустым состоянием.

Строки `page_layout` при этом не меняются: место освобождается только при выводе.

**Сетка «левый 1+1 и правый 1».** Размещение по сторонам карточки `parameter_sets.card_side` (`left` / `right`) переводится в трёхколоночную сетку по правилу «левый 1+1 и правый 1»: левая область карточки занимает две колонки (`1 + 1`: два слота по одной колонке либо один слот шириной две колонки, `column_start = 1..2`), правая колонка — одну (`column_start = 3, column_span = 1`).

Высота в строках задаёт занимаемую область сетки, а не фиксированную высоту содержимого в пикселях. На узком экране слоты следуют в порядке чтения одной колонкой. Неполный последний повтор показывает доступные элементы. При догрузке сохраняются курсор выборки и позиция в образце; граница порции не запускает рисунок заново. Повторный ответ на тот же запрос не должен удваивать элементы. Пустая выборка показывает состояние раздела. Частные рисунки «Проектов» и «Новостей» утверждаются отдельно.

## 5. Мультитекст и мини-игры

В существующем blocks_value вводится блок widget. Сериализованные поля — widget_id, entity_id при необходимости и необязательный design. Для модели допустимы дополнительные свойства вставки title, caption и height. Путь iframe закреплён за реализацией в каталоге. Порядок задаёт документ, виджет выводится по центру в доступной ширине. Автор выбирает определение из каталога, указывает сущность, видит превью и может переместить или удалить вставку как обычный блок. Отличие от карточки-блока Р-23: виджет вызывается напрямую, без сетки макета страницы; параметры виджета (widget_id, entity_id, design) хранятся в самом блоке Мультитекста, а не в page_layout. Сохранение и публикация проверяют UID и совместимость параметров одной транзакцией с сохранением самого материала; вставки с entity_id индексируются в document_entity_refs. Значение входит в существующую версию материала. Обратное открытие старой версии восстанавливает её вставки. Существующие блоки modelEmbed (в том числе 9 блоков в лекции 563) по мере модернизации сайта переводятся в виджеты; чтение прежних снимков с modelEmbed сохраняется. Для недоступной цели публичный вывод не раскрывает черновых данных; редактор видит причину в превью. При вложенном выводе текста повторное раскрытие того же материала в текущей цепочке останавливается.

Первый образец выбираем по инвентаризации клиентских компонентов. Для игры «Стили» до переноса сверить подбор зданий, годы, стили, формулировки, правила оценки, повтор игры и действующий адрес. Игровой движок становится виджетом. Если подбор редактируется автором, он хранится как версионируемая сущность с существующими видами параметров; её UID передаётся игре. Для постоянной игры допустим вызов без сущности. Счёт и ход текущей партии принадлежат экземпляру. Старый самостоятельный адрес должен открывать ту же игру. При инвентаризации отдельно отметить игры и интерактивные модели, чтобы не потерять материалы и не менять назначение модели без решения автора.

Зафиксировать контрольные страницы и версии для гостя и редактора. | У каждого элемента есть источник данных, назначение, владелец настройки и способ сверки. Редактор макета должен позволять выбрать страницу, создать копию макета, выбрать виджет из каталога, задать слот и дизайн, увидеть конфликт и проверить результат до назначения. Редактирование макета использует действующие права настройки, публикация материала — права его владельца и редакторов по правилам проекта. Эти проверки, аудит и резервирование входят в первый затронутый этап.

## 7. Решения перед реализацией

На согласование выносятся четыре таблицы (включая отдельную таблицу страниц pages) и поле назначения card, версия страницы как макет с указателем pages.current_layout_id, хранение фильтра у раздела, один источник раскладки карточки по типу, отдельное наследование layout_id, освобождение места пустыми виджетами, переключение макета через копию и порядок этапов. Первая реализация должна подтвердить их на реальной карточке, разделе, блоке Мультитекста и игре. Параметры конкретного дизайна, рисунки разделов и каталог вариантов каждой игры определяются при переносе.
