# ТЗ — виджеты и макеты страниц

19 ноября 2026 · Проект к согласованию. Основание — решение о виджетах карточки d1465e8 и последующее обсуждение универсального виджета, слота и типа страницы. Документ задаёт целевую модель и порядок перехода. Фактическая схема БД описана в [[Схема данных]], действующий механизм карточки — в [[Виджеты карточки — контракт]], первоначальное предложение — в [[Виджеты — проект схемы данных]].

## 1. Цель и результат

Собирать страницы из собственных компонентов проекта. Автор выбирает, что показать и в каком оформлении. Один зарегистрированный виджет можно использовать на карточке, на обзорной странице и внутри Мультитекста. Каждый виджет выполняет одну задачу. Другое содержательное представление получает собственное определение; тональность и оформление могут быть вариантами одного виджета.

Результат перехода — каталог виджетов, типы страниц, редактируемые макеты, серверное отображение страниц по макету и вставка в редакторе Мультитекста. Мини-игры входят в каталог на общих основаниях. Существующие URL, тексты, версии, подписи, источники, пользовательские настройки и права должны пережить переход.

## 2. Вызов виджета

Входные данные — UID показываемой сущности и необязательный вариант дизайна. Если по смыслу конкретному виджету сущность не нужна, его можно вызвать без UID. При пропущенном дизайне используется основной вариант. Виджет не получает как обязательный аргумент страницу, из которой его вызвали.

Каталог связывает UID с доверенной реализацией в коде. Реализация объявляет название для использования в редакторе, допустимые размеры, варианты дизайна и требования к входу. В БД хранится редактируемое название каталога; в коде достаточно исходного названия для регистрации. Разрешения на источники для каждого виджета не настраиваются. Компонент сам читает нужные данные через существующие механизмы видимости. Превью и публичный просмотр используют соответствующие доступные версии. Интерактивное поведение подключается к конкретному экземпляру, включая случай двух одинаковых игр в одном документе.

## 3. Структура БД

Имена ниже — целевые имена таблиц схемы app. Новые PK — uuid. Внешние ключи имеют тип PK соответствующей таблицы. У существующей сущности entities.id тип bigint. Название типа страницы, название виджета, слаг и имя реализации не используются для связей между записями.

| Таблица | Поля и ключи | Назначение |
|---|---|---|
| page_types | id UUID PK, name text NOT NULL | Справочник наименований типов страниц. Примеры — карточка сущности и страница раздела. Тип сущности по-прежнему задаёт entity_types. |
| widgets | id UUID PK, name text NOT NULL, renderer_key text UNIQUE NOT NULL | База виджетов для обеих сред вставки. renderer_key выбирает реализацию из кода. Переименование для редактора сохраняет UID. |
| layouts | id UUID PK, page_type_id UUID FK → page_types.id, name text NOT NULL | Именованный макет одного типа страницы. Один тип может иметь несколько макетов. |
| page_layout | id UUID PK, layout_id UUID FK → layouts.id, widget_id UUID FK → widgets.id, sort_order integer, row_start integer, column_start integer, row_span integer, column_span integer, design text NULL | Одна строка — один слот и занимающий его виджет. sort_order задаёт порядок чтения и заполнения. Геометрия относится к одному образцу сетки. design — вариант реализации, проверяемый при сохранении. |
| type_presentations (расширение) | layout_id UUID NULL FK → layouts.id | Для режима card выбирается макет карточки. Сохраняется наследование ближайшего представления вверх по дереву типов. compact и editor продолжают использовать действующую схему. |

Обязательны все поля слота, кроме design. Координаты начинаются с 1. Ширина и высота положительны; column_start + column_span − 1 ≤ 3. Внутри макета порядок уникален, прямоугольники не пересекаются. Сохранение перестановки проверяет всю итоговую композицию одной транзакцией. Два одновременных сохранения не должны молча затереть друг друга. Повтор одного widget_id в разных слотах разрешён. Размер проверяется по контракту выбранного виджета.

**Конкретная страница и макет.** Для карточки назначение хранится в type_presentations. Для существующих программных маршрутов разделов предлагается на первом этапе оставить владельцем выборки сам раздел: он задаёт фильтр, сортировку и UID назначенного макета в своей конфигурации. Тогда один макет можно использовать для разных выборок. Если понадобится управление назначениями разделов из БД, потребуется отдельно определить владельца назначения для маршрута. page_types хранит типы, а не экземпляры страниц. Размещение фильтра у раздела уточняет ранний вариант из проекта схемы.

**Версии и ссылки.** Изменение используемого макета влияет сразу на все назначенные страницы. Для первого выпуска предлагается создавать изменённый макет копией, проверять в превью и атомарно переключать назначение. Прежний макет остаётся доступен для возврата. Изменения каталога, макетов и назначений фиксируются с автором в действующем порядке аудита. Используемые определения нельзя физически удалять, в том числе при наличии вставок в исторических версиях Мультитекста. До реализации надёжной проверки таких ссылок каталог сохраняет определения.

## 4. Заполнение страницы

Карточка передаёт один UID своим слотам. Страница раздела формирует упорядоченную выборку и передаёт каждому следующему слоту UID очередной сущности. Фильтрация по видимости выполняется до заполнения. Чтобы при равенстве основного значения порядок воспроизводился, последним критерием сортировки служит UID. В БД хранятся слоты одного образца. Фактические повторы и карточки текущей выдачи строятся при чтении.

Высота в строках задаёт занимаемую область сетки, а не фиксированную высоту содержимого в пикселях. На узком экране слоты следуют в порядке чтения одной колонкой. Неполный последний повтор показывает доступные элементы. При догрузке сохраняются курсор выборки и позиция в образце; граница порции не запускает рисунок заново. Повторный ответ на тот же запрос не должен удваивать элементы. Пустая выборка показывает состояние раздела. Частные рисунки «Проектов» и «Новостей» утверждаются отдельно.

## 5. Мультитекст и мини-игры

В существующем blocks_value вводится блок widget. Сериализованные поля — widget_id, entity_id при необходимости и необязательный design. Порядок задаёт документ, виджет выводится по центру в доступной ширине. Автор выбирает определение из каталога, указывает сущность, видит превью и может переместить или удалить вставку как обычный блок. Сохранение и публикация проверяют UID и совместимость параметров. Значение входит в существующую версию материала. Обратное открытие старой версии восстанавливает её вставки. Для недоступной цели публичный вывод не раскрывает черновых данных; редактор видит причину в превью. При вложенном выводе текста повторное раскрытие того же материала в текущей цепочке останавливается.

Первый контрольный перенос — игра «Стили». До переноса сверить подбор зданий, годы, стили, формулировки, правила оценки, повтор игры и действующий адрес. Игровой движок становится виджетом. Если подбор редактируется автором, он хранится как версионируемая сущность с существующими видами параметров; её UID передаётся игре. Для постоянной игры допустим вызов без сущности. Счёт и ход текущей партии принадлежат экземпляру. Старый самостоятельный адрес должен открывать ту же игру. При инвентаризации отдельно отметить игры и интерактивные модели, чтобы не потерять материалы и не менять назначение модели без решения автора.

## 6. Этапы переработки и приёмка

| Этап | Работа | Условие завершения |
|---|---|---|
| 1. Инвентаризация и исходное состояние | Сопоставить маршруты, типы карточек, встроенные секции, настройки card_side, settings.card_widgets, стилистический виджет, блоки текста, игры и их адреса. Зафиксировать контрольные страницы и версии для гостя и редактора. | У каждого элемента есть источник данных, назначение, владелец настройки и способ сверки. До первой миграции выполнена и проверена процедура [[BackUp]]. |
| 2. БД и каталог | Добавить четыре таблицы, назначения для card, ограничения, реестр кода, чтение, аудит и разрешённую запись. Зарегистрировать определения с устойчивыми UID. | Повтор применения не создаёт дубликаты. Отвергаются битые ссылки, наложения, выход из сетки и потерянное конкурентное обновление. Отказ в записи и аудит успешной записи проверены. |
| 3. Карточка сущности | Обернуть существующие разделы в виджеты. Перенести порядок, стороны, явные и наследуемые настройки в макеты на копии БД; неоднозначные соответствия вынести на проверку. До переключения читать старую раскладку. | Сверены готовый HTML, ссылки, цитирование, технические параметры, изображения с подписями, черновик и публикация. Стилистический анализ выводится один раз в предусмотренном месте. Переключение и возврат испытаны. |
| 4. Страницы разделов | Подключить выборку и повторяемый макет к существующим маршрутам по одному. Сохранить адреса, фильтры и прежний смысл сортировки. | Проверены ноль результатов, неполный повтор, продолжение внутри образца, мобильный порядок, исходный HTML и индексируемые ссылки. |
| 5. Мультитекст | Реализовать вставку, выбор сущности, дизайн, превью, сохранение, публикацию и чтение старых версий. | Один виджет показывает одну сущность из сетки и из текста. Две вставки независимы. Исторический материал и документы без вставок открываются. |
| 6. Мини-игры | Перенести «Стили», затем остальные подтверждённые игры из инвентаризации. | Совпадают контрольные задания и результаты. Работают прежние адреса, сетка и текст, две партии на странице и повторный запуск. |
| 7. Переключение и завершение | Выпускать по типам страниц, сравнить публичный сайт и авторизованное превью, зафиксировать фактический выпуск и возможность отката в WIKI. | Для всех элементов этапа 1 есть проверенный результат. Старый механизм выводится из эксплуатации после сверки пользовательских настроек и проверки восстановления. |

Редактор макета должен позволять выбрать тип страницы, создать копию макета, выбрать виджет из каталога, задать слот и дизайн, увидеть конфликт и проверить результат до назначения. Редактирование макета использует действующие права настройки, публикация материала — права его владельца и редакторов по правилам проекта. Эти проверки, аудит и резервирование входят в первый затронутый этап.

## 7. Решения перед реализацией

На согласование выносятся четыре таблицы и поле назначения card, хранение фильтра у раздела, переключение макета через копию и порядок этапов. Первая реализация должна подтвердить их на реальной карточке, разделе, блоке Мультитекста и игре. Параметры конкретного дизайна, рисунки разделов и каталог вариантов каждой игры определяются при переносе.
