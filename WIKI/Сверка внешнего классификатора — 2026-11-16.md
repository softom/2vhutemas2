## Почему прямой перенос неприемлем

1. **Обход нашего API.** Новый обработчик кнопки в HTML (около строки 1344) выполняет `sb.from("features").upsert(...)` из браузера. Уже существующая форма также читает/пишет `projects`, `project_style`, `project_feature`, авторов и медиа напрямую. Новый код продолжает старую архитектуру, противоречащую Р-02: клиент ходит только в наш API.
2. **Публикация раньше сохранения.** Кнопка «Отметить» создаёт/обновляет признаки с `is_published: true` и `onConflict: "slug"`. Это может обновить существующий признак по совпавшему slug, а не по выбранному UID. Затем UI предлагает сохранить карточку, хотя запись признаков уже произошла. Отмена карточки её не отменяет; ошибки отдельных upsert игнорируются.
3. **Недостаточная авторизация исследования.** `handleSearchStyle` проверяет `supabase.auth.getUser(token)`, но не роль/право редактора. Затем используется клиент с service-role и серверные ключи платных провайдеров. Нет применения нашего principal, проверки edit и журнала AI-запросов.
4. **Потеря результата.** Исследование остаётся в DOM/`lastSearchAnalysis`. В штатное сохранение переносятся только ID выбранных стилей/признаков; источники, выдержки, фазы, зоны, отрицания и обоснования не сохраняются вместе с ними. Результат не привязан проверкой к версии и UID исследуемой карточки; переключение объекта после запроса требует отдельной защиты.
5. **Непроверенный ответ LLM.** Сервер выполняет JSON.parse без структурной валидации; `consensus_score` затем вставляется в innerHTML без экранирования. Нужны схема ответа, проверка UID по каталогу, допустимых значений и безопасный рендер.
6. **Ключи и качество источников.** UI хранит ключи провайдеров в localStorage. В нашем контуре ключи должны оставаться в серверной конфигурации. Из 50 результатов читаются страницы только первых 24; остальные — сниппеты, поэтому нельзя сообщать о 50 прочитанных статьях. `atob(rawData)` требует последующего декодирования байтов как UTF-8 для русского XML. Ошибки поисковых провайдеров и справочников сейчас скрываются. При серверном чтении внешних URL нужны ограничения адресов/редиректов и размера ответа.

Статический анализ не подтверждает работоспособность внешних провайдеров; запросы к ним не запускались.

## Предлагаемый способ объединения без потерь

1. Сохранить внешний прототип отдельным исходным артефактом/коммитом в его репозитории после проверки секретов; сохранить серверную поправку медиа отдельно от добавления исследования. Не включать остальные незакоммиченные файлы ArchSite в этот коммит. В этой сессии ArchSite не изменялся.
2. Сохранить и завершить текущие наши изменения публикации медиа отдельным коммитом с предусмотренными проверками. Затем делать перенос поверх этого состояния. Не заменять наши файлы целиком и не применять весь diff ArchSite к новому репозиторию.
3. Перенести полезную часть — сбор источников, анализ отрицаний, фаз, зон, раздельных уровней классификации — в серверный модуль нашего API. Вызывать его через защищённый маршрут досье с правом edit, учётом AI-запросов и проверкой версии. Timeline оставить обслуживать существующие чтения.
4. Результат сохранять как версионируемое предложение исследования внутри существующего эскиза/истории досье, вместе с источниками и признаками доступности текста. Точный JSON-контракт и его сохранение через нормализатор эскиза требуется реализовать: простое добавление неизвестного поля недостаточно. Новые таблицы и колонки здесь не предлагаются.
5. Сопоставлять предложения с текущими сущностями/параметрами/вариантами `app` по UID. Числовые ID старых `styles/features` нельзя считать UID соответствующих записей `app`. Если подходящего параметра или варианта нет, оставить явное предложение редактору; не создавать и не публиковать справочник автоматически. Физическое соответствие старых словарей новой модели требует отдельной сверки; рабочая БД в этой сессии не читалась.
6. Добавить панель исследования в текущий React-редактор эскиза. Отметки меняют только проверяемое предложение; применение — через существующий API утверждения, с транзакцией, аудитом, правами и конфликтами версий. Сохранять ручные правки, кандидатов/отложенные связи и media_manifest. Повторное исследование не заменяет просмотренную карточку молча.
7. До выкладки проверить: запрет гостю/читателю, отсутствие прямых обращений браузера к БД, отмену без публикации, сохранность источников/фаз/ручных правок, ошибочные UID/ответ LLM, переключение карточки, конфликт версий, повтор без дублей, публикацию медиа и отложенных связей. Перед отдельной будущей выкладкой — проверенная резервная копия и штатные smoke. Это план, не выполненные проверки.
