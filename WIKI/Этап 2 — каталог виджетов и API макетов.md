# Этап 2 — каталог виджетов и API макетов

20.11.2026. Реализация и интеграционные проверки на копии. Исходная производственная схема — 0064. В рабочем postgres проверены max(number)=64 и отсутствие app.page_layout. Подключение сетки к выводу карточки относится к этапу 3.

## Схема и версии

0065_widgets_pages.sql создаёт pages, widgets, layouts, page_layout и согласованный служебный audit_log. Начальные страницы: карточка, проекты, авторы, лекции, новости, о проекте. Указатели действующего макета пусты. Единственный начальный виджет — style_analysis; встроенные секции параметров и связей остаются в прежнем коде. UID определения разрешается через БД, ключ доверенного рендерера — через реестр кода. Начальный контракт style_analysis допускает ширину 1–3 и высоту 1, оформление default.

Строка layout_only в type_presentations хранит явное назначение макета типу, который ранее получал состав секций от предка. Выбор секций пропускает такие строки. Выбор макета ищет ближайший непустой layout_id, затем использует pages.current_layout_id карточки. Прежний макет после первого назначения защищён от правки и удаления. Порядок и пересечения проверяются для итогового состояния транзакции; для ограничения прямоугольников используется btree_gist.

## API

Префикс /api/v1/admin. Ведение общих определений следует существующему праву настройки su. Четыре GET: /widgets, /layouts/:id (в том числе превью копии), /pages/:id/layout и /type_presentations/:id/layout. Семь операций записи:

| Операция | Тело JSON |
|---|---|
| POST /widgets | name, renderer_key; реализация должна существовать в коде |
| POST /layouts | page_id, name |
| POST /layouts/:id/copy | name; копируются слоты с новыми UID |
| POST /page_layout | layout_id, expected_revision, widget_id, sort_order, row_start, column_start, row_span, column_span, design; id при обновлении. Для перестановки нескольких слотов — массив slots с общей expected_revision |
| DELETE /page_layout/:id | layout_id, expected_revision |
| POST /pages/:id/layout | layout_id, expected_layout_id (null при первом назначении), expected_revision целевого макета |
| POST /type_presentations/:typeId/layout | Те же поля. Ожидаемый UID — собственное назначение типа. Сброс через layout_id=null восстанавливает наследование |

После изменения слотов API возвращает макет с новым revision. Несовпадение ожидаемой версии или назначения даёт 409. Триггеры фиксируют создание виджета и макета, изменения слотов и переключения назначения одной транзакцией с UID автора и прежним/новым состоянием. У app_api отозваны полученные по умолчанию права прямого изменения audit_log.

## Проверки

Чистый dump восстановлен в widget_0065_integration_20261120. Полный SQL сначала выполнен с ROLLBACK и проверкой отсутствия таблиц, затем с COMMIT на этой копии. В ранней репетиции использовалась отдельная widget_stage1_verified_1795122071; эталонный dump остаётся в исходном зашифрованном резерве.

Deno check прошёл для основного приложения и интеграционного теста. api/tests/widgetLayouts_test.ts вызывает Hono-маршруты с тестовыми principal и реальными транзакциями роли app_api. Проверены отказ гостю (401), отказ editor без su (403), создание и чтение определения, копирование, удаление слота, неверный UID и дизайн, пересечение, выход за сетку, атомарный обмен местами и параллельные изменения с одной revision (один успех, один 409). Проверены наследование, явное назначение, сброс, общая раскладка, сохранение исходного состава секций, запрет назначения макета чужой страницы и правки ранее действовавшей версии.

Отдельные проверки PostgreSQL подтвердили четыре вида событий с автором, сохранение старого/нового состояния, совместный откат события и изменения, запрет прямого изменения журнала ролью API и запрет удаления используемых определений. Вход через браузер и выкладка новых маршрутов в production в эти проверки не входили.
