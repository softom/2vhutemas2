# Правила проекта

Приняты пользователем 2026-09-22. Главный источник решений и планов — WIKI в D:\WORK\2Vhutemas.

1. **Внутренние ссылки — только по UID.** Название, текст, slug, код словаря или отображаемое значение не используются как внешний ключ. UID — стабильный уникальный идентификатор записи; существующие bigint ID сохраняются до отдельного решения о миграции типов. Новым таблицам предлагается UUID. Внешние URL источников не являются внутренними связями БД.
2. **Данные сохраняем.** Проект учебный: перезапуски и временная недоступность допустимы. Собранные материалы и результат человеческой работы — основная ценность. Перезапуск не оправдывает удаление данных, потерю правок или сброс настроек.
3. **Изменения оформляем коммитами.** Код, миграции, настройки без секретов и WIKI версионируем в Git. В PostgreSQL ведём отдельный журнал изменений с UID, автором, Git SHA, миграциями и состоянием применения. Пользователь подтвердил: сам код хранится в GitHub, в БД — журнал, не полная копия репозитория.
4. **Все изменения, решения и планы записываем в WIKI.** Различаем принято, предложено, реализовано и проверено. Значимые решения фиксируем с датой и причинами; изменение решения сохраняет ссылку на прежнее.
5. **GitHub — удалённый репозиторий кода.** Локальные коммиты и запись в журнале БД — разные действия. Нельзя объявлять push, деплой или запись в журнал успешными без результата операции.
6. **BackUp — часть первого этапа.** Сохраняем всё, на что пользователь тратит время: материалы, оригиналы, версии, настройки, права, аккаунты, WIKI и код. Перечень источников и восстановление — на странице [BackUp](BackUp.md).
7. **Противоречия WIKI согласовываем.** Если предлагаемое решение противоречит действующей WIKI, предъявляем конкретное расхождение пользователю до зависимых изменений. После согласования обновляем связанные страницы. Явная новая инструкция пользователя является решением; повторного разрешения на ту же правку не требуется.
8. **Планы тоже входят в WIKI.** Важные договорённости не остаются только в переписке. Подтверждённые четыре этапа из таблицы экранов определяют план интерфейсов.

Операционные доступы и инфраструктурные секреты остаются в профильной WIKI/защищённом хранилище. Их не копируем в GitHub. Прежние схемы в нашей WIKI, использующие code как FK, являются историческим проектом и требуют приведения к правилу UID до SQL.

## Журнал изменений БД — проект

- `project_commits`: id UUID PK, author_id UID, git_sha (текстовый атрибут Git, не FK), summary, wiki_paths, created_at.
- `commit_migrations`: id UUID PK, project_commit_id FK по UID, migration_name, checksum. Имя миграции — атрибут, не связь на текст.
- `commit_applications`: id UUID PK, project_commit_id FK, environment_id FK, status (planned/applying/applied/failed), started_at, finished_at, error_summary.
- `deployment_environments`: id UUID PK, name; без ключей доступа.
- Версии материалов связываются с логическим изменением по project_commit_id, когда операция выполняется в рамках такого изменения. Git SHA обязателен для изменения кода, но не требуется отдельный Git-коммит на каждый пользовательский абзац.

Журнал добавочный: попытки и ошибки сохраняются. Для миграций, выполняемых одной транзакцией, успешный результат фиксируется согласованно с изменением. Для развёртывания сервиса отдельно фиксируется результат после проверки; одной транзакции между GitHub и сервером нет. При недоступности журнала операция не объявляется зарегистрированной, сохраняется локальный отчёт для последующей сверки. Импорт, права и настройки также требуют аудита.
