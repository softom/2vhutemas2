# Стек сущностей для внесения в БД

Принято 2026-11-11. Самостоятельный блок сайта, не подраздел новостей. Статус: решения и целевая схема; реализация, физическое хранение и миграции пока не выполнены.

## Два независимых результата

Сайт развивает сеть сущностей и связей. Материал может быть полезен для публикации события, для пополнения каталога или для обоих направлений. Отказ «неинтересно / старое / повтор» в новостях не означает отказ от извлечения сведений для БД и не должен обучать каталожный отбор такому отказу.

Блок 2.2 сопоставляет события и объединяет публикации разных изданий, сохраняя каждый исходник, медиа и происхождение. Число публикаций и число уникальных изданий различаются. После сопоставления работают независимые направления: 2.3–2.5 оценивают новость; 2.2.1 выделяет сущности и изменения для каталога. Повтор публикации не закрывает 2.2.1. Одно событие не равно одному объекту: у проекта бывают анонс, строительство, открытие и награды.

## 2.2.1 Разбор архитектурного материала

| Параметр | Результат |
|---|---|
| Объект / проект | Название и сопоставление с записью каталога |
| Автор / бюро | Человек и организация различаются; определяется роль, а не только упоминание |
| Типология | Сопоставление с существующим деревом типов сайта; не отдельный список робота и не категория новости |
| Место | Сопоставление с существующей сущностью места |
| Событие / стадия | Анонс, проектирование, строительство, открытие, участие, номинация, финал, победа |
| Источники и материалы | Основания каждого параметра и предлагаемой связи; текст, ссылки, медиа |

Для каждого сопоставления различаем: найдено по UID; неоднозначно; не найдено; нет сведений в источнике. Упоминание автора не доказывает авторство. Неоднозначности и противоречия предъявляются редактору. Архитектурный разбор применяется по содержанию, включая архитектурные конкурсы, а не только по категории «Архитектура».

Номинации и результаты связываются с конкретным конкурсом, годом/выпуском и номинацией, с подтверждающим источником. Участник, номинант, финалист и победитель не смешиваются. Так движение автора и проекта видно без обязательной публикации новости.

## Самостоятельный блок 5

В схеме номер 5 сохраняет прежние номера новостных блоков 1–4. Блок имеет самостоятельный вход в интерфейсе каталога.

Входы: предложения из 2.2.1; действие редактора «В каталог»; ручное задание пользователя — название, ссылки, файлы и заметки. Ручное задание не требует новости.

Единица стека — предложение создать сущность, дополнить существующую запись, подтвердить связь или приложить материалы, а не просто копия статьи. Задание содержит сопоставления с БД, предлагаемые параметры/связи, источники, материалы, причины решений. Несколько статей об одном объекте дополняют согласованное задание, сохраняя происхождение каждого сведения; противоречия требуют проверки, не автоматической перезаписи.

Шаги: **5.1 задание → 5.2 проверка → 5.3 готово к внесению → 5.4 применение и проверка результата**.

Статусы: **предложено → на проверке → готово к внесению → внесено**; отдельно **требует уточнения** и **отклонено с причиной**. «В каталог» не означает «уже внесено». Подтверждение редактора предшествует применению. «Внесено» — только после проверки результата, с сохранёнными UID и происхождением изменений.

Стек выпуска новостей и стек сущностей независимы. Действия редактора: только в новости; только в каталог; в оба; ни в один с причинами по направлениям. Новость может ссылаться на существующие сущности без создания новых записей.

## Ограничения и план реализации

Используем существующие основы модели: запись, связь, параметр и версии. Внутренние связи только по UID. Создание самостоятельного функционального блока не означает разрешение произвольных новых таблиц: сначала сопоставить требования со «Схемой данных», затем отдельно определить физическое хранение.

1. Разобрать пример KAI: существующие сущности, источники, разные события и недостающие связи.
2. Спроектировать сопоставление и форму проверяемых предложений; разделить решения/обратную связь новостей и каталога.
3. Реализовать общий стек с ручным входом и входом из обработки материалов.
4. Реализовать подтверждение, применение и проверку результата: права, аудит, BackUp и сохранность данных обязательны с первого этапа. Повторное применение не создаёт дубли; ошибка не помечает всё задание выполненным.

Проверочные сценарии: повтор новости с новыми данными для каталога; ручное задание без новости; существующий автор и новый проект; неоднозначное авторство; конкурс с номинацией/результатом; несколько источников одного задания; конфликт сведений; повторное применение без дублей.
