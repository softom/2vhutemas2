# ТЗ — настройки исследований и единая форма наборов

18.11.2026. Согласовано пользователем 18.11.2026; выпуск реализован и проверен 19.11.2026; ограничения и результаты — в [журнале выпуска](Настройки%20наборов%20и%20общая%20форма%20—%202026-11-18.md). Проверены локальные миграции 0016, 0017, 0026, 0040, 0058, 0061 и API parameters.ts. Фактическая схема сервера в этой проверке не опрашивалась. Состояние реализации и проверки фиксируются отдельно; этот документ не подтверждает применение миграции.

## 1. Цель и границы

Расширить существующие parameter_sets и parameter_set_items. Наборы «Что» и «Стилистические решения» остаются существующими записями с прежними UID. Одна форма панели и одна форма предложений обслуживают все наборы по их определениям. Различаются типы полей и серверные операции, но не самостоятельно написанные сценарии для каждого набора.

Согласованное распределение:

- У набора: задания исследования, поисковые профили, назначение результатов и разрешённые цели записи.
- У параметра в составе набора: порядок, обязательность/повторяемость, оформление, инструкция заполнения, дополнение/повторы и требования к доказательствам.
- У определения параметра: общий смысл, тип данных, единица, варианты и ограничения типа ссылки. Значения сущностей не являются настройками формы.

Описываем расширение определения, не переносим пользовательские значения и не создаём новые сущности предметной области. Решение об удалении исследования из стека создания отдельно ещё не принято; это ТЗ не разрешает такое изменение.

## 2. Что уже есть

| Таблица | Используемые существующие поля |
|---|---|
| app.parameter_sets | id UUID, code, title_ru, note, sort_order, card_side |
| app.parameter_set_items | составной PK (set_id, parameter_id), sort_order, hint |
| app.parameters | id, code, title_ru, definition, value_type, unit, is_repeatable, is_published, value_entity_type_id, row_set_id, авторство/даты |
| app.parameter_options | варианты значений параметра по UID |
| app.type_parameter_sets / entity_parameter_sets | применимость и прикрепление, включая attached_at у прикрепления к сущности |

Не создавать заново порядок, подсказку, размещение слева/справа, определение типа или публикацию. Табличные значения уже описываются через parameters.row_set_id: колонки — параметры вложенного набора; их порядок и оформление также должны читаться из parameter_set_items.

Важные расхождения с желаемой моделью:

1. is_repeatable сейчас глобальный, а не свойство вхождения. БД запрещает повтор одиночного параметра независимо от набора.
2. PUT состава сейчас принимает code и выполняет DELETE всех строк + INSERT. При расширении заменить на обновление по UID с сохранением отсутствующих в запросе настроек; явное удаление вхождения отделить от изменения порядка.
3. Значение сейчас не даёт автоматически однозначный контекст набора, если параметр входит в несколько наборов. Перед введением разных правил повторяемости нужна проверка происхождения значения и путей записи. Нельзя выбирать правило первого случайного набора.
4. Нет готового версионирования полного определения набора, его заданий и состава. Номер версии сам по себе историю не сохраняет.

## 3. Предлагаемое расширение parameter_sets

| Новое поле | Тип / начальное значение | Назначение |
|---|---|---|
| research_enabled | boolean, false | Возможность исследования; включить для перенесённых действующих профилей |
| result_kind | text, parameter_values | parameter_values или relations; одно назначение на набор в первом выпуске |
| config_version | bigint, 1 | Оптимистическая блокировка; увеличивается при изменении набора, состава, заданий или профилей |
| created_at / updated_at | timestamptz | Аудит определения; для старых данных не выдавать дату миграции за дату первоначального создания |
| created_by / updated_by | UUID FK contributors, nullable для старых записей | Авторство настройки |

Разрешённые параметры для результата parameter_values определяются составом набора и признаком research_enabled у вхождения. Не хранить второй расходящийся список параметров в JSON.

Для результата relations разрешённые типы понятий и роли задавать связями набора с существующими UID типов/ролей. Предлагаемые служебные таблицы parameter_set_allowed_types(set_id, type_id) и parameter_set_allowed_roles(set_id, role_id), составные PK и настоящие FK к действующим справочникам. Точное имя таблицы ролей сверить при проектировании SQL. Не использовать названия и code как внутренние ключи.

## 4. Подчинённые набору задания и поисковые профили

Это составные части определения набора, а не независимая библиотека исследовательских продуктов. Новые служебные таблицы ниже — предложение, требующее согласования перед SQL.

### parameter_set_research_tasks

| Поле | Тип | Назначение |
|---|---|---|
| id / set_id | UUID PK / UUID FK parameter_sets | Постоянный UID задания и владелец |
| title / instruction | text | Название и задание LLM |
| sort_order / enabled | integer / boolean | Порядок и доступность |
| model_name | text, nullable | Разрешённая сервером модель; без секретов и произвольного endpoint |
| max_calls / max_source_chars | integer, nullable | Профиль бюджета, не выше серверного потолка |

Версия задания входит в общую config_version набора. Результат запуска фиксирует task_id и версию конфигурации. Если включено несколько заданий, интерфейс явно выбирает задание; не запускать все автоматически и не умножать расходы молча. В первом переносе — одно активное задание на набор.

### parameter_set_search_profiles

| Поле | Тип | Назначение |
|---|---|---|
| id / set_id | UUID PK / UUID FK | UID профиля и набор |
| language_tag | text | Язык запроса |
| title_source | text enum | title_ru, title_en, title_original; заданная цепочка fallback |

| sort_order / enabled | integer / boolean | Порядок и включение |

Если нужен список провайдеров — валидируемый список поддерживаемых сервером кодов, а не URL для отправки секретов. Никаких исполняемых выражений, SQL или произвольных инструкций загрузчику в шаблонах. Шаблоны языков и тематические слова отбора перенести из researchQueries.ts/researchBudget.ts в настройки профиля; технический алгоритм отбора остаётся общим. Структуру списка тематических слов определить в JSON-схеме профиля, без внутренних ссылок на сущности по названиям.

## 5. Расширение parameter_set_items

Сохраняем PK (set_id, parameter_id): новые настройки относятся к конкретному вхождению параметра. Не дублируем существующие sort_order и hint.

| Новое поле | Тип / начальное значение | Назначение |
|---|---|---|
| label_override | text, nullable | Подпись вместо parameters.title_ru в этом наборе |
| input_kind | text, auto | Авто по типу либо разрешённый совместимый вид ввода |
| is_required | boolean, false | Требование к принятому результату/публикации; пустой черновик сохраняется |
| repeatability | text, inherit | inherit, single, multiple; ограничения реализации ниже |
| summary_order | integer, nullable | Какие поля и в каком порядке образуют краткое представление строки |
| research_enabled | boolean, true | Может ли исследование предлагать это поле |
| fill_instruction | text, nullable | Указание LLM для поля в данном наборе |
| merge_policy | text, inherit | replace, append_unique или supplement_relation; допустимость зависит от назначения и типа |
| dedup_policy | text, inherit | Проверяемая сервером стратегия повтора, не произвольный код |
| source_required | boolean, false | Требуется источник |
| quote_required | boolean, false | Требуется точная цитата, следовательно source_required=true |
| minimum_evidence | text, snippet | snippet, partial, page; для атрибуций переносится действующее page |
| phase_required / zone_required | boolean, false | Необходимость контекста при принятии |
| result_slot | text, nullable | Для relations: слот общего результата — concept, relation, quote, rationale, source, phase, zone |

Конкретные enum и совместимость фиксируются в API/БД. Нельзя select для несовместимого типа, supplement_relation для обычного числа или заполнение неизвестного слота. Для связей создать/сопоставить определения полей в составе набора, но не записывать их как вторую таблицу значений сущности: адаптер сохраняет штатную связь и цитату. Прежние строки style_solutions не становятся новыми полями автоматически и остаются сохранены.

Составной ключ позволяет ссылаться на вхождения без дополнительного UID. Если правило повтора содержит список полей-ключей, хранить их через FK на вхождения/параметры соответствующего набора, а не свободные имена колонок. Для таблиц ключи относятся к вложенному row_set_id. Источник/роль/фаза/зона атрибуции — части явной стратегии связи.

### Повторяемость и конфликт правил

is_repeatable у параметра сохраняется как текущая техническая возможность и значение по умолчанию. В первом переносе repeatability=inherit сохраняет поведение. single может ограничивать ввод в наборе, но не удаляет ранее сохранённые повторы. multiple нельзя включить при глобальном запрете БД.

Полноценная разная повторяемость одного параметра в разных наборах — отдельный обязательный подпункт реализации: проверить, где хранится контекст набора у группы/значения, и предложить минимальное расширение при его отсутствии. Не снимать глобальное ограничение без замены и проверки остальных наборов. Аналогично применяется обязательность: неизвестные данные не выдумываются ради заполнения формы; показывается причина невозможности принять результат.

## 6. Версии, права и журнал

Любое изменение определения требует ожидаемую config_version и права управления справочниками (сейчас su). Полный снимок набора, состава, заданий и профилей сохранять атомарно в предлагаемой служебной parameter_set_config_revisions: (set_id, version), snapshot JSONB, created_at, created_by. Это архив определения, не второй действующий источник настроек. Снимки неизменяемы; удаление используемого определения ограничивается, применяется отключение.

Запуск сохраняет set_id, task_id, config_version, фактическую модель/бюджет и использованный корпус в служебном результате. Изменение настроек не меняет уже запущенное исследование. Старые результаты без версии явно обозначаются как прежние, им не приписывается вымышленная конфигурация. Секреты остаются вне этих таблиц.

## 7. Общая форма и серверные операции

Один компонент панели, один компонент списка предложений, общие элементы поля по value_type/input_kind. API возвращает нормализованное предложение: UID цели/вхождения, было, будет, действие, доказательства, статус проверки и возможность выбора.

У всех наборов одинаковые расположение чекбокса, массовый выбор, порядок информации и единственное действие сохранения выбранного. Проверка автоматическая, до выбора; сервер повторяет её при записи. Для обычных параметров показывается выбор группы, для связей — применимые поля цели; это условные поля общей формы по схеме, не отдельный компонент принятия для каждого набора.

Серверные адаптеры parameter_values и relations выполняют различные транзакции, но не возвращают отдельную разметку. Нельзя проверять название/code набора для выбора формы, задания или поисковых слов. Разрешённый технический result_kind выбирает адаптер. Типы, права, UID, точность цитат, безопасность загрузчика, лимиты и аудит остаются проверяемым кодом.

## 8. Перенос и приёмка

1. Перед SQL сверить реальную схему, существующие расширения и конкурентные правки; согласовать конкретные новые таблицы/колонки. Проверенный backup и восстановленная тестовая копия — до миграции.
2. Добавить расширения без изменения UID, значений, истории, прав и публикации. Старые настройки переносятся с прежним поведением; неизвестное авторство не выдумывается.
3. Переделать API состава с DELETE/INSERT на сохранение по UID; отсутствие расширенных полей в старом запросе не стирает их. Явное удаление вхождения не удаляет значения сущностей.
4. Перенести действующие задания, языковые запросы и правила из кода; отдельно проверить «Что», стили и площадную программу с вложенными колонками.
5. Подключить общие формы и адаптеры; проверить выбор, повторы, конфликты версий, отказы и атомарность. Платные вызовы не требуются для проверки интерфейса: использовать сохранённые результаты и тестовые ответы.
6. Проверить одинаковый сценарий на desktop/mobile; один параметр в двух наборах с разными подсказками не меняет другой набор. Проверить гостевой доступ, скрытые тексты и сохранность старых значений.
7. Критерий универсальности: новый набор с поддерживаемыми типами и result_kind подключается только данными, без нового TSX и правок условий по его code.
8. Выпуск только после проверок, записи результата в WIKI и согласованной выкладки. Полный редактор настроек — последующий этап; API, права и версии нужны сразу.
